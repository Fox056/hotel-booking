# Hotel Booking Platform

Платформа бронирования для отелей: наличие и цены, брони с онлайн-оплатой, синхронизация с каналами продаж. Пет-проект, который строится по практикам продакшена: микросервисы, контракты до кода, CI, наблюдаемость, учения по инцидентам.

Сейчас идёт этап 2 из 6, контракты и ADR. Кода пока нет, план — в разделе [План](#план).

## Цели

Стартовые целевые показатели: они ещё не измерены и проверяются нагрузочными тестами и тестами на сбои. Условия измерения и остальные требования — в [PRD](docs/prd.md#6-нефункциональные-требования).

| Требование | Цель |
|---|---|
| Овербукинг из собственных продаж | ни одной брони сверх наличия, даже при одновременных запросах |
| Задержка изменения наличия до каналов | p95 не больше 10 с для точечных изменений |
| Создание брони на стенде | p95 не больше 300 мс при 50 RPS |
| Падение Channel Sync или канала | прямые брони продолжают приниматься |
| Простой RabbitMQ до 5 минут | исходы броней не меняются |
| Потеря событий | ноль: outbox и at-least-once, дубли безвредны благодаря идемпотентности |

## Сервисы

| Сервис | Владеет данными | Принимает | Публикует |
|---|---|---|---|
| inventory | отели и типы номеров, наличие, цены, удержания | REST: наличие и цены, поиск, типы номеров; внутренний REST: удержать / подтвердить / снять, продажа из канала; справочные данные отеля, типы номеров и наличие для channel-sync | `availability.v1` |
| booking | брони, саги, ключи идемпотентности, персональные данные гостей | REST создания, статуса и отмены брони; команды броней из каналов, исходы оплаты и итоги сверки через RabbitMQ | `booking.v1` |
| payment | журнал списаний и возвратов | команды списания, возврата и запроса статуса через RabbitMQ; `booking.v1` | `payment.v1` |
| channel-sync | подключения и сопоставления, состояние каналов, принятые вебхуки, записи на ручном разборе | `availability.v1`, вебхуки каналов | команды в booking |
| gateway | — | внешний трафик | готовый Traefik: TLS, маршруты, лимиты |

Плюс `fake-externals`: заглушки платёжного провайдера и каналов продаж с настраиваемыми задержками, ошибками 5xx и 429.

У каждого сервиса своя база. В чужую базу сервисы не ходят, только через API или события. Кто какими данными владеет и какие копии держит, описано в [ADR-0002](docs/adr/0002-service-boundaries-and-data-ownership.md).

- Синхронный REST — когда клиенту нужен ответ сразу, например удержание номеров при создании брони.
- Команды через RabbitMQ — когда ответ не нужен сразу: оплата, возврат, брони из каналов. Повторы живут в базе сервиса.
- События через Kafka — для изменений, на которые реагируют другие сервисы: наличие, статусы броней и платежей.

Правило выбора, повторы и поведение при отказах описаны в [ADR-0003](docs/adr/0003-sync-and-async-interactions.md).

## Сага бронирования

Оркестратор — booking.

1. Удержание номеров в inventory: синхронно, идемпотентно, с TTL 15 минут. Без свободных номеров — сразу 409.
2. Оплата: команда в payment, повторы с backoff.
3. Подтверждение — точка невозврата. Удержание превращается в продажу, уходят события.
4. Компенсации. Сбой оплаты снимает удержание. Отмена после подтверждения освобождает номера, а бесплатная отмена ещё и возвращает деньги. Если оркестратор упал, удержания с истёкшим TTL освобождает сам inventory.

Состояния брони, сроки, компенсации и поздние исходы оплаты описаны в [ADR-0004](docs/adr/0004-booking-saga.md).

Брони из каналов приходят вебхуком. Канал уже продал номер, поэтому такую бронь нельзя просто отклонить. Если номеров не осталось, бронь принимается с флагом овербукинга и алертом для ручного переселения.

## Принципы

- Событие пишется в outbox в той же транзакции, что и данные. Доставка at-least-once, дубли отсекают inbox и идемпотентность. Механика outbox, inbox и очередей в базе — в [ADR-0005](docs/adr/0005-outbox-and-inbox.md).
- Внешние вызовы не делаются внутри транзакции БД.
- Повторный запрос не создаёт второй брони: создание брони требует `Idempotency-Key`.
- Ошибки API отдаются в формате Problem Details.

## Безопасность и требования законов

- Персональные данные гостей (152-ФЗ): только нужные поля, маскирование в логах. Шифрование чувствительных полей и обезличивание по сроку хранения — после этапа 6.
- Оплата: данные карт не хранятся, только токены провайдера. Чеки по 54-ФЗ отправляет провайдер, в заглушке это событие «чек отправлен».
- Вебхуки каналов подписаны HMAC, у каждого канала свой API-ключ.
- Ключи и токены проверяют сами сервисы, а не шлюз. Внутренний вызов подписан коротким токеном сервиса, без него запрос отклоняется. Решения описаны в [ADR-0007](docs/adr/0007-access-and-authentication.md).
- Секреты хранятся вне репозитория.

## Наблюдаемость

Трейсы OpenTelemetry проходят через HTTP, Messenger и Kafka. Correlation id — это trace id из `traceparent`: он есть в каждом логе и в ответах сервисов с ошибкой. Логи в JSON и трейсы собирает Grafana Alloy и отправляет в Loki и Tempo, метрики собирает Prometheus, дашборды — в Grafana. Персональных данных в телеметрии нет: атрибуты спанов и поля логов проходят по разрешённому списку, IP-адрес клиента не пишется.

Алерты — правила Prometheus с тестами, уведомления отправляет Alertmanager в Telegram. Среди них отставание консьюмеров, непустая DLQ, зависшие саги, доля ошибок, задержка синхронизации с каналами. Каждый алерт срабатывает на учении или в сценарии проверки на стенде. Решения описаны в [ADR-0006](docs/adr/0006-observability.md).

## Учения по инцидентам

Запланированы на этапе эксплуатации. Для каждого сценария заранее зафиксировано ожидаемое поведение, по каждому учению будет постмортем в `docs/postmortems/`.

| Сценарий | Ожидаемое поведение |
|---|---|
| Kafka недоступна 10 минут | брони принимаются, события копятся в outbox и уходят после восстановления |
| Провайдер оплаты отвечает 5xx | повторы с backoff, затем DLQ; удержания освобождаются по TTL |
| Канал отвечает 429 | лимит и circuit breaker, остальные каналы не тормозят |
| Шторм дублей вебхуков | ни одной лишней брони |
| Консьюмер упал посреди пачки | после рестарта дубли отсекает inbox |
