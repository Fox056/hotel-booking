# ADR-0001: Монорепозиторий и структура

- Статус: принято
- Дата: 2026-10-20
- Уточнён: [ADR-0006](0006-observability.md) — correlation id это trace id из `traceparent`, отдельного заголовка нет

## Контекст

Платформа состоит из четырёх сервисов — inventory, booking, payment и channel-sync — и общего пакета `platform` с инфраструктурным кодом: outbox, inbox, обёртки Kafka и Messenger, correlation id, Problem Details, OpenTelemetry. Контракты пишутся до кода. Рядом с сервисами нужны заглушки внешних систем и окружение docker compose. Каждое изменение ревьюит один техлид, разработка идёт на Windows в docker compose.

Нужно решить, сколько заводить репозиториев и как сервисы получают общий код и контракты. Требования к решению:

- контракт и все его потребители меняются и проверяются вместе;
- сервисы не зависят от кода друг друга;
- CI проверяет только то, что затронуто изменением, и не блокирует пул-реквест, в котором поменялась только документация.

## Варианты

1. **Монорепозиторий.** Сервисы, `platform`, `contracts/`, заглушки и `deploy/` — в одном репозитории.
   - Плюсы: контракт и все его потребители меняются одним пул-реквестом и проверяются вместе; одно окружение разработки и один CI; `platform` не нужно выпускать версиями.
   - Минусы: CI должен выбирать проверки по изменённым путям; сервисы легко связать общим кодом; CI проверяет все сервисы на одном коммите, хотя деплоятся они в разное время.
2. **Репозиторий на сервис** и отдельные репозитории для `contracts/` и `platform`.
   - Плюсы: независимые релизы и права доступа; связать сервисы общим кодом труднее.
   - Минусы: одно изменение контракта — три-четыре пул-реквеста и выпуск версии пакета; локальное окружение собирается из нескольких репозиториев. Для команды из одного техлида выгода не окупает расходы.
3. **Гибрид:** сервисы в одном репозитории, `contracts/` и `platform` — отдельными пакетами с версиями.
   - Плюсы: сервисы обновляют общий код независимо, а по версии пакета видно, какие форматы понимает каждый сервис.
   - Минусы: изменение контракта не проверить вместе с потребителями в одном пул-реквесте; каждое изменение общего кода — это выпуск версии и обновление во всех сервисах.

## Решение

Монорепозиторий со структурой из [README](../../README.md#структура) и правилами ниже.

### Границы кода

- У каждого сервиса свой `composer.json` и свой автозагрузчик, а path repository сервиса указывает только на `platform`, это проверяет CI. Поэтому класс соседнего сервиса просто не найдётся. Общее — только `platform` и `contracts/`.
- В `platform` только инфраструктура: без доменной логики и без классов событий и команд сервисов. Классы сообщений каждый сервис держит у себя и проверяет по схемам из `contracts/`. Иначе общий пакет превратит сервисы в распределённый монолит: изменение класса события пришлось бы выкатывать во все сервисы одновременно.
- Заглушки `fake-externals` — отдельное приложение, код сервисов они не используют.

### Форматы `platform` — тоже контракт

Конверт сообщения с заголовком `traceparent`, формат Problem Details описываются в `contracts/` и меняются только обратно совместимо, по тем же правилам, что схемы событий и команд. Сервисы деплоятся в разное время, поэтому совместимость нужна в обе стороны: старая версия сервиса читает сообщения новой, а новая — старые, в том числе те, что ждут в очередях, outbox и DLQ. Тесты сервисов на одном коммите такое расхождение не поймают, его ловит проверка совместимости схем с версией из `main`.

Сообщения между сервисами кодирует сериализатор из `platform`: тип сообщения и заголовки берутся из `contracts/`, а имена PHP-классов — ни сообщений, ни штампов Messenger — в передаваемое сообщение не попадают. Служебные данные Messenger, без которых не работают повторы, например счётчик повторов, сериализатор переносит в своих заголовках из конверта, тоже без имён классов. Failure transport у каждого сервиса свой, поэтому для него подходит стандартный сериализатор.

### Подключение `platform`

- Сервисы подключают `platform` через Composer path repository, без семантических версий: сервис всегда берёт `platform` из того же коммита, а изменение `platform` проверяет CI всех сервисов.
- В разработке Composer ставит симлинк, корень репозитория монтируется в контейнер целиком. В образах — копия (`COMPOSER_MIRROR_PATH_REPOS=1`), чтобы `vendor/` не ссылался за пределы сервиса.
- Зависимости и автозагрузку `platform` Composer берёт из `composer.lock` сервиса, а не из `platform/composer.json`. Поэтому пул-реквест, который меняет `platform/composer.json`, обновляет и `composer.lock` всех сервисов. CI для каждого сервиса обновляет `platform` в lock-файле и падает, если файл изменился.
- Версия `platform` задаётся явно в настройке path repository. Иначе Composer выводит её из текущей ветки, и lock-файлы менялись бы от ветки к ветке.

### Пространства имён

У сервисов — `Inventory\`, `Booking\`, `Payment\` и `ChannelSync\`, у пакета — `HotelBooking\Platform\`. Стандартное для Symfony `App\` рассчитано на одно приложение в проекте, а здесь их четыре в одном репозитории:

- Встроенные сериализаторы Symfony Messenger передают полное имя класса вместе с сообщением: `PhpSerializer` — в теле, сериализатор на основе Symfony Serializer — в заголовке `type`. При одинаковом `App\` обмен между сервисами заработал бы по совпадению имён PHP-классов, и эти имена незаметно стали бы частью контракта. С разными пространствами имён такой обмен ломается на первом же тесте, поэтому тип сообщения берётся из контракта.
- Все сервисы создаются из одного шаблона. При `App\` одинаковые полные имена классов оказались бы в одном проекте IDE по четыре раза, и переход к определению уводил бы в чужой сервис.
- По имени класса в стеке вызовов и в логе сразу видно сервис.

### Контракты

`contracts/` — источник правды: тесты сервисов проверяют ответы API и сообщения по OpenAPI, AsyncAPI и JSON Schema из этой папки.

### Сборка образов

- Контекст сборки — корень репозитория, `.dockerignore` тоже в корне: инструкция `COPY` не видит файлов вне контекста, а сервису нужны `platform/` и `contracts/`.
- Dockerfile сервиса копирует только `platform/`, `contracts/` и свой сервис, сохраняя раскладку репозитория, чтобы относительный путь к `platform` из `composer.json` работал и в образе. Правка соседнего сервиса не сбрасывает кеш слоёв.
- `.dockerignore` исключает `.git`, а по всему дереву — `**/vendor`, `**/var`, `**/.env.local`, `**/.env.*.local` и `**/*.md`. Шаблон без `**/` в `.dockerignore` действует только в корне контекста.
- Каждый сервис собирается в свой образ и деплоится отдельно.

### CI

- Проверки пул-реквеста — один workflow без фильтра `paths`. Если фильтр пропустит весь workflow, его обязательная проверка останется в состоянии Pending и заблокирует мерж, см. [документацию GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks#handling-skipped-but-required-checks).
- Первая job определяет изменённые пути. Job сервисов, `platform`, контрактов и заглушек запускаются по условию `if`; job, пропущенная по условию, считается успешной.
- Job проверок зависят только от job определения путей. Если job зависит от другой job, которую пропустили, GitHub пропускает и её: проверка не выполняется, но засчитывается как успешная.
- Изменения в `platform/`, `contracts/`, `deploy/compose/`, `.github/` и `.dockerignore` запускают проверки всех сервисов.
- Обязательная проверка для `main` — одна итоговая job. Она зависит от всех job проверок, запускается с `if: always()` и падает, если любая из них упала или была отменена. Без `always()` итоговую job пропустили бы при падении зависимости, пропущенная job засчиталась бы как успешная, и сломанный пул-реквест смержился бы. Новая job проверок обязательно добавляется в зависимости итоговой, иначе её падение не заблокирует мерж.

## Последствия

- Проще: контракт и его потребители меняются одним пул-реквестом, окружение разработки и CI одни на всё, `platform` не выпускается версиями.
- Сложнее:
  - CI выбирает проверки по путям и держит итоговую job;
  - обратную совместимость форматов `platform` обеспечивают дисциплина и проверка схем, а не версии пакета;
  - свои пространства имён нужно один раз прописать в шаблоне сервиса: в автозагрузке, `services.yaml`, маршрутах, маппинге Doctrine, `public/index.php`, `bin/console` и настройках MakerBundle, PHPUnit и PHPStan.
- Остающиеся риски — в [реестре рисков](../risks.md): среда разработки на Windows (Р-20) и несовместимое изменение форматов (Р-7).
- Когда пересмотреть: если сервису понадобится обновлять `platform` независимо от остальных или понадобятся отдельные права доступа к его коду. Тогда сервис выносят в отдельный репозиторий вместе с историей (`git subtree split`), а `platform` начинает выпускать версии.
