# Глоссарий

Единый язык проекта. Документы пишутся по-русски, код и контракты — по-английски, поэтому у каждого термина есть английское имя. Определения следуют [PRD](prd.md). Имена полей и значения перечислений даны в snake_case. Английские имена рабочие: окончательно их закрепляют контракты v1.

## Наличие и цены

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Отель | hotel | Объект размещения на платформе. У отеля свои часовой пояс (IANA), время заезда, типы номеров, цены и подключённые каналы. |
| Время заезда | check_in_time | Местное время суток, с которого отель заселяет гостей. По умолчанию 14:00. |
| Тип номера | room type | Категория номеров, которую продают как единицу наличия. Конкретный номер отель назначает при заселении, вне системы. |
| Вместимость | capacity | Сколько гостей принимает один номер типа. |
| Снять с продажи | deactivate, `active: false` | Тип номера перестаёт продаваться, но не удаляется. Не путать со «снять» (`release`) из бронирования. |
| Ночь | night | Единица проживания и наличия. Проживание — ночи в полуинтервале [дата заезда, дата выезда). |
| Дата заезда, дата выезда | check_in_date, check_out_date | Границы проживания по датам отеля. Дата выезда в ночи брони не входит. |
| Дата отеля | hotel local date | Текущая дата в часовом поясе отеля — «сегодня» для этого отеля. От неё считаются горизонт продаж и самая ранняя дата заезда. |
| Горизонт продаж | sales horizon | 365 дней: ночи брони лежат в полуинтервале [сегодня, сегодня + 365 дней), где «сегодня» — дата отеля. |
| Наличие | availability | Сведения о номерах типа на ночь: выставлено, продано, удержано, остаток, превышение. Изменения наличия и цен публикуются событием `availability.v1`. |
| Версия значения | version: `epoch`, `number` | Монотонно растущая версия значения по ключу события: у наличия и цены — по связке «отель, тип номера, дата», у брони — по брони. Сравнивается сначала по эпохе, затем по номеру. Не даёт устаревшему значению перезаписать более новое. |
| Выставлено | offered | Сколько номеров типа отель выставил на продажу на ночь. Если отель ничего не выставил, — ноль. |
| Продано | sold | Номера, проданные по подтверждённым прямым броням и по броням из каналов. |
| Удержано | held | Номера в действующих удержаниях. |
| Остаток | remaining | Выставлено − продано − удержано, наружу не меньше нуля. Гость и каналы видят именно остаток. |
| Остаток на период | remaining_for_stay | Минимум остатка по ночам периода. Его показывает поиск наличия и цен. |
| Превышение | oversold | Сколько номеров на ночь продано сверх выставленного. Возникает только из-за броней из каналов. |
| Цена за ночь | price | Цена типа номера на дату в рублях, хранится в целых копейках. Это конечная цена для гостя. |
| Тариф | rate plan | Тарифный план — набор условий продажи со своими ценами. В первой версии тарифных планов нет: у типа номера одна цена за ночь. |
| Сумма брони | amount | Сумма цен ночей брони, умноженная на число номеров. Считается сервером в момент удержания и фиксируется в брони. |
| Ожидаемая сумма | expected_amount | Сумма, которую клиент передаёт при создании брони. Если она не совпала с суммой сервера, ответ — «сумма изменилась». |

**Не путать.**
- **Овербукинг** — само явление: продано сверх выставленного.
- **Превышение** (`oversold`) — сколько номеров продано сверх выставленного на конкретную ночь. Это число меняется.
- **Флаг овербукинга** (`overbooked_on_acceptance`) — историческая отметка брони из канала, принятой при нехватке номеров.

## Бронирование

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Бронь | booking | Заказ номеров одного типа в одном отеле на непрерывные ночи. |
| Прямая бронь | direct booking | Бронь, которую гость создаёт через API платформы и сразу оплачивает. |
| Бронь из канала | channel booking | Бронь, которую канал присылает вебхуком. Канал уже получил оплату, поэтому бронь подтверждается сразу и не отклоняется из-за нехватки номеров. |
| Внешний id брони | external_id | Идентификатор брони в канале. Вместе с каналом и видом вебхука — бронь или отмена — он делает повторный вебхук безопасным. Уникален в пределах канала, во всех его отелях. До 128 символов: латиница, цифры, `_` и `-`. Приходит в теле вебхука, в пути и строке запроса его нет. Косвенный идентификатор гостя: в событиях, логах и алертах его нет. |
| Число номеров | rooms | Сколько номеров в брони. В прямой брони — от 1 до 5. |
| Число гостей | guests | Сколько гостей заселяется. В прямой брони его указывает гость, в брони из канала — канал. |
| Данные гостя | guest: `first_name`, `last_name`, `email`, `phone` | Имя, фамилия, email и необязательный телефон гостя прямой брони. У брони из канала все поля необязательны. Это персональные данные (П-15), в ответах гостевых операций их нет. |
| Удержание | hold | Временное резервирование номеров под прямую бронь по принципу «всё или ничего». |
| Срок удержания | expires_at | Момент, когда удержание истекает: через 15 минут после создания. Удержание истекает по сроку, а не по факту освобождения номеров. |
| Подтвердить | confirm | Превратить удержание в продажу. Это точка невозврата прямой брони. Подтвердить удержание после его срока нельзя. |
| Снять | release | Снять удержание или продажу по брони. Для продажи из канала сначала гасится превышение. Повтор безопасен. После «снять» по этой брони остаётся отметка, и «удержать», «подтвердить» и продажа из канала отказывают. |
| Продажа из канала | channel sale | Продажа без удержания, допускает превышение. |
| Овербукинг | overbooking | Продажа сверх выставленного. Из собственных продаж исключён; бронь из канала с овербукингом принимается. |
| Флаг овербукинга | overbooked_on_acceptance | Отметка брони из канала, принятой при нехватке номеров. Ставится один раз и не снимается, даже если превышение потом погасилось. |
| Статус брони | booking status | `pending_payment` — ожидает оплаты, `confirmed` — подтверждена, `not_confirmed` — не подтверждена, `cancelled` — отменена. |
| Причина «не подтверждена» | not_confirmed_reason | `payment_declined` — оплата отклонена: провайдер отказал или по запросу статуса деньги не списаны; `payment_outcome_unknown` — нет исхода оплаты; `hold_not_confirmed` — удержание не подтверждено; `force_closed` — завершена принудительно. |
| Статус возврата | refund status | `none` — нет, `in_progress` — в процессе, `completed` — выполнен, `failed` — не удался. |
| Источник брони | source | `direct` — прямая, `channel` — из канала. |
| Момент заезда | check_in_at | Дата заезда и время заезда отеля в его часовом поясе, переведённые в абсолютное время. Если такого местного времени нет из-за перевода часов, берётся ближайший следующий момент; если оно встречается дважды — первый. Фиксируется в брони при создании. |
| Срок бесплатной отмены | free_cancellation_until | Момент заезда минус 24 часа абсолютного времени. Фиксируется в брони при создании. |
| Бесплатная отмена | free cancellation | Отмена не позже срока бесплатной отмены: номера освобождаются, деньги возвращаются полностью. |
| Невозвратная отмена | non-refundable cancellation | Отмена после срока бесплатной отмены, но до момента заезда: номера освобождаются, деньги не возвращаются. |
| Токен брони | booking token | Секрет, который гость получает при создании брони. По нему гость смотрит и отменяет бронь. Начинается с `bt_`, в брони хранится только его хеш. |
| Ключ идемпотентности | idempotency key, заголовок `Idempotency-Key` | UUID v4 или v7, который генерирует клиент, регистр не важен. Делает повтор создания брони безопасным. Привязан к отелю из пути и к телу первого запроса, хранится 24 часа. Не путать с ключом идемпотентности платежа. |
| Согласие | consent: `accepted`, `text_version` | Согласие гостя на обработку персональных данных с версией текста. Для броней из каналов его получает канал. |
| Обезличивание | anonymization | Замена персональных данных брони через 30 дней после выезда, отмены или перехода в «не подтверждена». Для email откладывается, пока исход оплаты не выяснен или возврат «в процессе» или «не удался», но не дольше 90 дней. Суммы, даты и статусы остаются. |

## Ошибки API

Ошибки отдаются в формате Problem Details. Свой тип — у отказов, которые клиент различает по смыслу. У отказов без смысла сверх кода HTTP, например 401, 403, 404 публичных операций, 413 и 503, тип — `about:blank`. Здесь основные типы, полный каталог — в [README контрактов](../contracts/README.md#каталог-типов). 429 шлюз отдаёт обычным текстом.

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Нет мест | no_availability | Остатка не хватает хотя бы на одну ночь. Код 409. |
| Сумма изменилась | amount_changed | Сумма сервера не совпала с ожидаемой. Код 409, в ответе текущая сумма. |
| Удержание истекло | hold_expired | Повтор создания брони пришёл, когда удержание уже истекло или снято или до его срока меньше минуты. Код 409, итог сохраняется под ключом идемпотентности: бронь создаётся заново с новым ключом. |
| Нет ключа идемпотентности | idempotency_key_missing | Запрос создания брони пришёл без ключа идемпотентности. Код 400. |
| Запрос ещё выполняется | request_in_progress | Запрос с этим ключом идемпотентности ещё не завершён. Код 409. |
| Ключ не совпадает с телом | idempotency_key_mismatch | Тот же ключ идемпотентности пришёл с другим отелем или телом запроса. Код 422. Повтор с тем же отелем и телом законен. |
| Отмена невозможна | cancellation_not_allowed | Бронь нельзя отменить: момент заезда наступил, бронь в статусе «ожидает оплаты» или «не подтверждена» или это бронь из канала. Код 409. |
| Ниже проданного | offered_below_committed | Отель выставляет меньше номеров, чем продано и удержано, хотя бы на одну дату. Код 409, в ответе список дат. |
| Ошибка валидации | validation_error | Запрос не прошёл проверку. Код 422. |
| Удержание завершено | hold_finished | Внутренний API inventory: удержание брони истекло, снято или его не было. Код 409. Гость получает «удержание истекло». |
| Бронь снята | booking_released | Внутренний API inventory: у брони стоит отметка «снято», поэтому запоздавшая продажа из канала отказывает. Код 409. |
| Отель не найден | hotel_not_found | Внутренний API inventory: отеля из пути нет. Код 404. |
| Отель не совпал | hotel_mismatch | Внутренний API inventory: отель из пути не совпадает с отелем брони. Код 409. Это отказ конфигурации, а не ответ по существу. |

## Оплата

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Списание | charge | Полная предоплата прямой брони по одноразовому токену карты. |
| Ключ идемпотентности платежа | payment_idempotency_key | Ключ, с которым payment обращается к провайдеру. Строится по брони и виду операции, у списания и возврата он разный. Повтор с тем же ключом не создаёт второго списания, по нему же запрашивается статус платежа. Не путать с ключом идемпотентности клиента (`Idempotency-Key`). |
| Возврат | refund | Возврат денег: при бесплатной отмене, при компенсации или по итогам сверки платежей. |
| Токен карты | card token | Одноразовый токен провайдера вместо данных карты. Данные карт в платформу не попадают. |
| Исход оплаты | payment outcome | Что booking знает о списании: `none` — сообщений ещё не было, `charged` — списано, `not_charged` — не списано, то есть провайдер отказал или по запросу статуса денег нет, `unknown` — неизвестно. Неизвестный исход не затирает известный, а «списано» побеждает «не списано». |
| Исход не выяснен | payment outcome unresolved, `payment_outcome_unresolved` | У брони «не подтверждена» исход оплаты `none` или `unknown`, при любой причине. Пока исход не выяснен, обезличивание email откладывается, а сверка платежей ищет исход у провайдера. |
| Крайний срок списания | charge deadline | Срок удержания. После него новых попыток списания нет, только запрос статуса платежа. |
| Окно попыток списания | charge attempt window | Время, когда payment может вызывать провайдера: 10 минут с первой попытки, но не позже крайнего срока минус запас 30 с. Вне окна — только запрос статуса. |
| Статус платежа | payment status | Ответ на запрос статуса по ключу идемпотентности платежа: `charged` — списано, `not_charged` — не списано, `unknown` — неизвестно. Нужен, когда ответ на списание потерялся. |
| Сверка платежей | payment reconciliation | Ежедневное сравнение списаний и возвратов с данными провайдера. Проверяет все неподтверждённые прямые брони. Если по брони, которая так и не была подтверждена, деньги списаны, а возврата ещё нет, они возвращаются. Здесь же окончательно выясняется исход для броней, у которых он не выяснен. |
| Чек | receipt | Чек по 54-ФЗ: чек предоплаты 100 % при списании и чек возврата при возврате. Формирует провайдер. |
| Чек отправлен | receipt sent | Событие, которым заглушка провайдера заменяет выдачу чека. |

## Каналы

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Канал продаж | channel, `channel_id` | Внешняя площадка (OTA), которая продаёт номера отеля. В первой версии — заглушки. Id канала — короткий код из конфигурации, например `ota-alpha`, а не UUID: каналы — закрытый набор, и код служит меткой метрик. |
| Подключение канала | channel connection | Связь канала с отелем, задаётся конфигурацией. Канал, который обращается к неподключённому или несуществующему отелю, получает 403. |
| Синхронизация | sync | Отправка в канал абсолютных значений остатка и цены по паре «тип номера, дата». |
| Склейка | coalescing | Объединение частых изменений перед отправкой в канал. |
| Состояние канала | channel state | Последние значения, которые подтвердил канал. Устаревшее значение не перезаписывает более новое. |
| Сопоставление | mapping, `room_type_code` | Соответствие типов номеров отеля кодам типов номеров канала. Задаётся конфигурацией. Отель канал знает по нашему id. |
| Сверка с каналами | channel reconciliation | Ежедневное сравнение остатков и цен на 30 дней вперёд с состоянием канала. Расхождения отправляются заново. |
| Вебхук | webhook | Входящий запрос канала с бронью или отменой, подписанный HMAC с меткой времени: заголовки `X-Signature` и `X-Timestamp`. Каждую попытку доставки канал подписывает заново. |
| Запись на ручном разборе | unprocessed channel reservation | Бронь из канала, которую нельзя обработать автоматически: тип номера не сопоставлен, в брони несколько типов номеров, ночи за горизонтом продаж, типы номеров или даты не отвечают контракту вебхука, внешний id уже пришёл для другого отеля или бронь не помещается в команду для booking. Канал получает 2xx. До разбора это запись в channel-sync, а не бронь: в booking и в списке броней отеля её нет. Отмена такой записи запоминается и применяется после разбора. Неверные данные гостя на разбор не отправляют: поле отбрасывается, бронь проходит. Отмена с внешним id, который уже пришёл в отмене для другого отеля, тоже ждёт разбора: такая запись хранит только ключ и отель, без данных гостя. |

## Сага и надёжность

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Сага | saga | Последовательность шагов создания прямой брони: удержание, списание, подтверждение. Оркестратор — booking. |
| Компенсация | compensation | Шаг, который отменяет сделанное при сбое: снять удержание, вернуть деньги. |
| Точка невозврата | point of no return | Подтверждение удержания. После него бронь можно только отменить. |
| Зависшая сага | stuck saga | Бронь, которая находится в статусе «ожидает оплаты» дольше срока удержания плюс 5 минут. Закрывается принудительно. |
| Outbox | outbox | Таблица исходящих сообщений, которая пишется в той же транзакции, что и данные. Отдельный процесс — relay — отправляет их в брокер. После подтверждённой отправки тело стирается, а id остаётся на 8 дней для сверки НФТ-7. |
| Inbox | inbox | Таблица принятых сообщений: потребитель, id и день создания сообщения, время приёма. Повторная доставка не даёт повторного эффекта. Запись о принятом вебхуке в channel-sync — его данные, а не inbox. |
| Окно inbox | inbox window | 7 дней по часам базы. Сообщение старше окна обрабатывается без записи в inbox, и дубль отсекает защита предметной области: версия, ключ платежа, пара «канал, внешний id», состояние брони. |
| Конверт сообщения | envelope | Объект JSON в теле сообщения, общий для событий и команд: id сообщения, тип, время создания, межсервисные заголовки, версия ключа, id изменения и данные `payload`. Служебные штампы Messenger в конверт не входят, они лежат в заголовках транспорта. Формат описан в контрактах и меняется только обратно совместимо. Не путать с классом `Envelope` в Symfony Messenger — это объект внутри процесса. |
| Тип сообщения | message type, `type` | Имя схемы сообщения с основной версией: `<область>.<имя>.v<N>`, например `booking.state.v1`. У события область — имя топика без версии. |
| Эпоха | epoch | Часть версии значения. Растёт после восстановления базы владельца из резервной копии: полный снимок новой эпохи побеждает старые события тех же ключей. Ключи, которых в снимке нет — данные, потерянные при восстановлении, — остаются в топике со старой эпохой до конца срока хранения, поэтому до тех пор копии перестраиваются из выгрузки владельца. |
| Изменение издателя | change, `change_id` | Одно изменение издателя: запись одной транзакцией, например наличия на диапазон дат, или один запуск команды публикации, например полного снимка после восстановления. Его id общий у всех сообщений изменения. Не путать с id операции, который несут фоновые шаги. |
| Срок хранения ПДн сообщения | `pii_retain_until` | Заголовок конверта у команды с ПДн: момент, после которого все копии сообщения стирают ПДн, если он наступает раньше 30 дней от создания. У событий его нет. |
| At-least-once | at-least-once | Доставка хотя бы один раз. Дубли безвредны благодаря идемпотентности. |
| DLQ | DLQ | Очередь сообщений, которые не удалось обработать после повторов. Их разбирает дежурный. |
| Failure transport | failure transport | Итоговая DLQ сервиса на Symfony Messenger: таблица в его базе, куда попадает сообщение, которое не удалось записать, или фоновый шаг, исчерпавший повторы. |
| Фоновый шаг | background step | Работа сервиса, поставленная в очередь в его базе в той же транзакции, что и данные: вызов другого сервиса или внешней системы со своими повторами. Несёт только id операции. Воркеры опрашивают очередь, уведомлений PostgreSQL нет. |
| Relay | relay | Процесс, который отправляет записи outbox в брокер. У Kafka и RabbitMQ relay разные. Relay опрашивает outbox; в Kafka на сервис активен один relay, чтобы после compaction у ключа не осталась устаревшая версия. |
| Строка outbox на разборе | parked outbox row | Строка, которую брокер не принимает, например сообщение больше лимита. Она переезжает в отдельную таблицу и даёт алерт, тело живёт не дольше 30 дней и срока хранения ПДн сообщения. В отправку её возвращает консольная команда сервиса; событие compacted-топика так не возвращают — владелец публикует текущее состояние новой версией. |
| Заменённое событие | superseded event | Строка outbox compacted-топика, у ключа которой уже отправлена версия новее. Relay её не отправляет: событие несёт полное состояние ключа, и более новая версия его уже содержит. |
| Отложенное сообщение | deferred message | Сообщение Kafka, которое консьюмер не смог обработать. Оно ждёт повтора в таблице потребителя, а чтение партиции продолжается. |
| Альтернативный обменник | alternate exchange | Обменник RabbitMQ, куда брокер направляет сообщения, которым некуда попасть, а через dead-letter — сообщения сверх лимита доставок и те, что не удалось разобрать. Его очередь разбирает эксплуатация. |
| Compaction | compaction | Режим топика Kafka, при котором для каждого ключа со временем остаётся только последнее значение — последнее по смещению, а не по версии. По такому топику копию можно перестроить с нуля, кроме времени после восстановления базы владельца: тогда в топике остаются ключи старой эпохи, и копию перестраивают из выгрузки владельца. |
| Экземпляр сервиса | service instance | Один деплой сервиса: пул обработчиков HTTP и процессы консьюмеров, обработчиков фоновых шагов, relay и планировщиков. На стенде по одному экземпляру каждого сервиса. |
| Воркер | worker | CLI-процесс, который по одному забирает сообщения из очереди и обрабатывает их. |
| Circuit breaker | circuit breaker | Временно прекращает запросы к каналу после серии ошибок, чтобы он не тормозил остальные. |
| Correlation id | correlation id | Trace id из заголовка `traceparent` (W3C Trace Context), отдельного заголовка нет. Проходит через все сервисы и сообщения, попадает в логи, журнал шлюза и ответы сервисов с ошибкой (`trace_id`). |
| Problem Details | Problem Details | Формат ошибок API (RFC 9457). Типы ошибок — в разделе [«Ошибки API»](#ошибки-api). |
| Шлюз | gateway | Точка входа внешних запросов: TLS, маршруты, лимиты. Ключи и токены проверяют сами сервисы. Инфраструктура, а не контекст. |
| API-ключ | API key | Секрет отеля (`hk_`) или канала (`ck_`) в заголовке `Authorization`. Сервис хранит только его хеш и по нему устанавливает личность запроса. |
| Личность запроса | request identity | Кто сделал запрос: отель, канал, гость брони или сервис. Её устанавливает `platform` по учётным данным, и по ней сервис ограничивает доступ к данным. |
| Токен сервиса | service token | Короткий JWT, которым сервис подписывает внутренний вызов: кто вызывает, кого и каким запросом. Действует 60 с и только для этого запроса. |
| Дежурный | on-call | Инженер, который получает алерты и разбирает DLQ, неудачные возвраты и записи на ручном разборе. |
| Сигнал | signal | Метрика или событие в логе с постоянным именем. Алерты строятся по метрикам, события в логах нужны для разбора. |
| Алерт | alert | Уведомление дежурному по правилу на сигнале. |
| Heartbeat | heartbeat | Метрика «последний такт» процесса. Такт ставится только после здоровой итерации, а алерт сравнивает число процессов со свежим тактом с ожидаемым. Поэтому видны и упавший, и остановленный, и ждущий базу процесс. |
| Сценарий проверки алертов | alert check scenario | Прогон на стенде, который создаёт условие алерта — данные со сдвинутым временем, сбой через Toxiproxy или сдвиг часов — и сохраняет срабатывание в отчёт. Вместе с учениями показывает, что каждый алерт работает (НФТ-15). |

## Данные сервисов

| Термин | В коде и контрактах | Определение |
|---|---|---|
| Владелец данных | data owner | Сервис, который единственный меняет определённые данные и отвечает за них. Остальные сервисы получают эти данные через его API или события. |
| Справочные данные отеля | hotel reference data | Часовой пояс и время заезда отеля. Ими владеет inventory, остальные сервисы получают их от него. |
| Проекция | projection | Копия чужих данных, которую сервис строит из событий владельца. Отстаёт от источника, обновляется только данными владельца и перестраивается из них. |
| Снимок | snapshot | Значение, зафиксированное в момент операции, например сумма брони или момент заезда в брони. Хранится как собственные данные того, кто его зафиксировал, и не меняется вслед за источником. |
| Внутренний API | internal API | Операции сервиса для других сервисов платформы, например «удержать». Через шлюз наружу не публикуются. |
