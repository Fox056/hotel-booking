# Контракты

Контракты пишутся до кода: сначала меняется файл здесь, потом сервис. Версия — в имени файла, `*.v1.*`. Внутри версии изменения только обратно совместимые ([ADR-0001](../docs/adr/0001-monorepo-and-structure.md)).

Тексты в самих контрактах — описания, `summary`, `title` ошибок — на английском, как код. Этот файл — по-русски, как остальная документация.

## Раскладка

| Файл | Что внутри |
|---|---|
| `openapi/common.v1.yaml` | общие компоненты: схемы безопасности, параметры, заголовки, схемы общих полей, ответы фронта и шлюза. Операций нет |
| `openapi/inventory.v1.yaml` | публичный API inventory: наличие и цены отеля, поиск |
| `openapi/inventory-internal.v1.yaml` | внутренний API inventory для booking: «удержать», «подтвердить», «снять», продажа из канала |
| `openapi/booking.v1.yaml` | публичный API booking: создание брони, статус, отмена |
| `openapi/channel-sync.v1.yaml` | публичный API channel-sync: вебхуки броней и отмен каналов |
| `openapi/channel-stub.v1.yaml` | API канала, которое реализуют заглушки: приём наличия и цен от channel-sync |
| `asyncapi/events.v1.yaml` | топики Kafka: настройки, ключи и сообщения, издатель и группы потребителей |
| `schemas/problem-details.v1.json` | Problem Details всех сервисов: общая форма и каталог типов |
| `schemas/envelope.v1.json` | конверт сообщений: общая форма и определения его полей |
| `schemas/availability.v1.json`, `schemas/booking.v1.json`, `schemas/payment.v1.json` | сообщения топиков: закрытая схема каждого типа, ключ и данные |
| `redocly.yaml`, `lint/`, `tests/`, `bin/check.sh`, `bin/lint-probe.js` | линтер контрактов и его тесты; `bin/lint-probe.js` — служебный плагин `check.sh`, через него скрипт видит, что Redocly прочёл и обошёл |
| `bin/compat.sh`, `bin/compat.js`, `tests/compat/` | проверка совместимости с базовой ревизией и её тесты |
| `bin/redocly.sh` | образ Redocly CLI и изолированный запуск, общие для обеих проверок |

Публичные документы сервисов и есть список операций, которые публикует шлюз ([ADR-0002](../docs/adr/0002-service-boundaries-and-data-ownership.md)). Внутренний API — отдельный документ, шлюз его не публикует. Документ с пометкой `x-implemented-by: fake-externals` в корне описывает API внешней системы, которое реализуют заглушки. Шлюз его тоже не публикует, см. «[Протокол заглушек каналов](#протокол-заглушек-каналов)».

## Проверка

```sh
bash contracts/bin/check.sh
```

Нужен Docker. Линтер — Redocly CLI 2.60.0 из образа, закреплённого по digest; обновление образа — отдельный пул-реквест. Скрипт проверяет:
- документы OpenAPI и AsyncAPI — рекомендованным набором Redocly и правилами этого репозитория, а примеры — по их схемам;
- что каждое своё правило срабатывает на своей фикстуре-нарушителе из `tests/rules/` и молчит на контрольной;
- что имена каталогов здесь не префиксы друг друга (см. «Подмножество OpenAPI 3.1»);
- что в `openapi/` и `asyncapi/` лежат только документы `*.yaml`, в `schemas/` — только файлы `*.json`, а контракты не ссылаются на заглушки из `tests/`. Иначе контракт проверялся бы по заглушке, а файл в другом виде ускользнул бы от проверок;
- что проверка совместимости (ниже) на каждой паре «база — изменение» из `tests/compat/` находит ровно то, что записано в её `expected.txt`, и что у каждого вида находки есть пара;
- что Redocly читает каждый документ — контракты, фикстуры и вспомогательные документы `tests/` — как `openapi: 3.1.<n>` или `asyncapi: 3.0.0`. Документ другой версии проходит lint с кодом 0, но ни одно правило этого репозитория на нём не запускается: с `openapi: 3.0.3`, `3.2.0` или `asyncapi: 2.6.0` контрольная фикстура прошла бы, ничего не проверив. В каталоге `openapi` лежит OpenAPI, в каталоге `asyncapi` — AsyncAPI, а вне `tests/compat/` в `tests/` есть только `*.yaml`, `*.json` в каталогах `schemas` и `expected.txt`;
- что каждую запись `$defs` в `schemas/` обходит lint хотя бы одного документа из `openapi/` или `asyncapi/`. На запись, к которой не ведёт ни один `$ref`, не действует ни одно правило схем, а сервисы проверяют сообщения по этим файлам напрямую. По той же причине в корне файла схем нет ничего, кроме `$schema`, `title`, `description` и `$defs` хотя бы с одной записью: корень Redocly не обходит. Исключение одно — открытая общая форма Problem Details в корне `problem-details.v1.json`. Её поля правила схем не проверяют, а меняются они только ломающим изменением, которое ловит проверка совместимости. Обход записи даёт ей только правила схем. Правила места персональных данных и правила событий действуют на запись, только если до неё доходит операция или сообщение канала, а не одна ссылка из `components`;
- что `apis` в `redocly.yaml` выключают правила для отдельного документа ровно по списку `RULE_OVERRIDES` в `check.sh`, а у записи `apis` нет ключей, кроме `root` и `rules`. Фикстуры проверяются общей конфигурацией и переопределения для одного документа не видят. Блок `apis` скрипт читает строгим разбором текста: строку, которую разбор не знает, он считает ошибкой;
- что неверная опция правила плагина роняет прогон: фабрика правила отвергает такую опцию, в том числе незнакомую, и только это не даёт ей тихо ослабить правило.

Новые проверки скрипт тоже проверяет на заведомо неверных данных: документах другой версии в `tests/versions/`, раскладке `tests/definitions/` с её `expected.txt`, вариантах `redocly.yaml` в `tests/overrides/` и конфигурациях с неверной опцией в `tests/options/`.

Правила линтера держат соглашения ниже:
- у API: явный `security`, `x-callers`, набор ответов, их медиатипы и типы ошибок по коду, пути только под `/v1/` и `/internal/v1/`, разрешённые имена параметров, место персональных данных и токена брони, точный состав тел запросов с персональными данными и тел вебхуков, закрытые схемы тел запросов и ответов, форма вебхуков каналов;
- у сообщений: поля конверта, закрытые схемы, имена полей событий из разрешённого списка и строки без свободного текста, ключ только из id и дат, настройки топиков и доступ к ним;
- у всех схем: пределы значений, шаблоны, которые держат строку целиком и читаются одинаково обоими движками, имена свойств в ASCII snake_case и подмножество OpenAPI 3.1.

Смысл правил — что повтор «удержать» отдаёт тот же снимок, порядок проверок, сроки хранения — линтер не проверяет: это проверяют тесты сервисов.

У документа внешней системы в `redocly.yaml` выключены три правила нашего API, см. «[Протокол заглушек каналов](#протокол-заглушек-каналов)».

Две особенности Redocly 2.60.0 для AsyncAPI:
- примеры сообщений он не проверяет. Поэтому скрипт собирает документ AsyncAPI со всеми ссылками, переносит примеры в служебный документ OpenAPI и проверяет их тем же правилом, что примеры OpenAPI. Заголовки примера проверяются по заголовкам сообщения, а пример с заголовками у сообщения без них — ошибка. Эту проверку скрипт тоже проверяет: на документах `tests/examples/` с заведомо неверными примерами она должна падать;
- в `topicConfiguration` биндинга Kafka он знает не все ключи, хотя биндинги Kafka 0.5.0 разрешают любые. `min.compaction.lag.ms` в тип добавляет плагин `lint/plugin.js`.

### Совместимость с базовой ревизией

```sh
bash contracts/bin/compat.sh [<база>]
```

Скрипт сравнивает `contracts/` рабочей копии с базой по правилам «Версии и совместимость сообщений».
- База — коммит, ветка или тег, по умолчанию merge-base текущей ветки и локальной `main`: перед запуском `main` стоит обновить.
- `contracts/` базы выгружается `git archive` и сравнивается в том же образе Redocly, без сети. Если в базе `contracts/` нет, всё считается новым.
- Каждое найденное изменение печатается с вердиктом и местом `<файл>#<JSON Pointer>`, совместимые тоже.
- Код выхода 1 — есть ломающее изменение или сравнить не удалось, 2 — неверный аргумент или нет Docker. Другой код — сбой окружения, например не запущен Docker.

## Соглашения

### Пути и имена

- Публичные операции — `/v1/…`, внутренние — `/internal/v1/…`. Внутренний префикс на шлюзе закрыт. Вебхуки каналов — `/v1/channels/{channel_id}/hotels/{hotel_id}/…`, см. «[Каналы](#каналы)».
- Сегменты пути — kebab-case. Поля, параметры и значения перечислений — snake_case, имена — из [глоссария](../docs/glossary.md).
- Отель — в пути у всех операций отеля, у создания брони и у вебхуков: `POST /v1/hotels/{hotel_id}/bookings`. Статус и отмена брони адресуются id брони: `/v1/bookings/{booking_id}`.
- Id — UUID в нижнем регистре. Неверно оформленный id в пути — 404: такого ресурса быть не может.
  - Исключение — id канала: короткий код из конфигурации, от 1 до 32 символов — строчные латинские буквы, цифры и дефис, первая — буква. Например, `ota-alpha`. Каналы — закрытый набор, как сервисы, а код канала служит меткой метрик ([ADR-0006](../docs/adr/0006-observability.md): значения меток — из закрытых наборов, id в метках не бывает).
  - У публичных операций этот 404 отдаёт сервис. Если в id есть символы, которые шлюз не пропускает, 404 отдаёт сам шлюз, без `trace_id`.
  - У внутренних операций такой 404 приходит без типа, то есть вне контракта: id брони формирует сам booking, и неверный id — его ошибка. Тесты inventory такой ответ по OpenAPI не проверяют.
- В пути и строке запроса нет персональных данных, токенов и внешних id броней каналов ([ADR-0006](../docs/adr/0006-observability.md)).

### Данные

- Деньги — целые копейки, поля валюты нет: в v1 только рубли.
- Даты отеля — `YYYY-MM-DD`. Диапазон дат — полуинтервал `[from, to)`, как ночи брони `[check_in_date, check_out_date)`.
- Моменты — RFC 3339 в UTC, без долей секунды: `YYYY-MM-DDThh:mm:ssZ`. Исключение — `created_at` конверта сообщений, см. «Конверт».
- Нет значения — нет поля, `null` не используется. Например, `not_confirmed_reason` есть только у статуса `not_confirmed`.
- У каждого значения есть предел:
  - у строки — `maxLength`, перечисление или формат `date` или `uuid`. Другие форматы длину не ограничивают: у email `maxLength: 254` (RFC 5321), у моментов `date-time` — 20, потому что RFC 3339 разрешает долю секунды любой длины;
  - у массива — `maxItems`;
  - у целого — `minimum` и `maximum` или перечисление.

### Тела запросов и ответов

- **Тела публичных запросов закрыты.** Неизвестное поле — 422 с кодом `unknown_property`, `pointer` ведёт на родительский объект: имя поля задаёт клиент, и в ответ оно не попадает.
- **Тела внутренних запросов открыты**: незнакомые поля игнорируются. Сервисы деплоятся в разное время, и вызывающий может прислать новое необязательное поле раньше, чем его узнает вызываемый.
- **Тела вебхуков каналов открыты**: незнакомые поля игнорируются и не сохраняются. На 4xx канал доставку не повторяет, и закрытое тело теряло бы бронь из-за нового поля канала, см. «[Каналы](#каналы)».
- Незнакомые параметры строки запроса игнорируются, кроме вебхуков: у них любая строка запроса, даже пустая «?», — 401.
- **Схемы ответов закрыты**, это проверяет линтер: тесты производителя ловят поле, которого нет в контракте, в том числе случайно попавшие в ответ персональные данные. Клиенты незнакомые поля игнорируют, в том числе booking в ответах inventory.
- **Общие поля «удержать» и создания брони** — `room_type_id`, `check_in_date`, `check_out_date`, `rooms` и `expected_amount`. Они лежат на верхнем уровне обоих тел, под одинаковыми именами и со схемами из `common.v1.yaml`. Поэтому `pointer` и `code` из 422 «удержать» booking отдаёт гостю без перевода. Общими бывают только схемы отдельных полей, а не объект: закрытый объект нельзя собрать через `allOf`.
- **Общие поля брони из канала.** Число номеров брони из канала и продажи из канала — одна схема `ChannelRooms`: бронь в пределах контракта вебхука проходит продажу. Данные гостя прямой брони и брони из канала — схемы `PersonName`, `Email` и `Phone`. Схемы `ChannelId`, `ExternalId` и `ChannelGuests` тоже лежат в `common.v1.yaml`: на них сошлётся команда брони из канала.

### Совместимость

- Внутри v1 изменения только обратно совместимые, и в запросах, и в ответах (ADR-0001).
- **Новое необязательное поле ответа — совместимое изменение, даже если схема ответа закрыта.** Закрытость проверяет только производитель в своих тестах, а клиенты незнакомые поля игнорируют. Для Problem Details этого требует RFC 9457 (раздел 3.2), для остальных ответов это правило этого репозитория. Сначала поле появляется в контракте, потом в коде.
- Новый код в `errors[].code` — тоже совместимое изменение: список открытый.
- Ослабить шаблон поля запроса, например под формат токена настоящего провайдера, — совместимое изменение.
- Схему поля, на которую ссылается схема сообщения, меняют по правилам сообщений, см. «Версии и совместимость сообщений».
- Схема Problem Details тоже меняется по правилам сообщений (ADR-0001), её сравнивает проверка совместимости. Новое необязательное поле в закрытом типе и новый тип совместимы, а новое поле в открытой корневой схеме ломает.

### Персональные данные и токены

- В ответах гостевых операций нет персональных данных гостя и токена карты. Это касается и ответа 201, который хранится под ключом идемпотентности 24 часа, и ответов статуса, отмены и ошибок. Токен брони есть только в ответе 201.
- Персональные данные приходят только в теле создания брони и в теле вебхука брони из канала: имя, фамилия, email и необязательный телефон (П-15 PRD); у брони из канала необязательны все поля. Паспортных данных и свободных комментариев нет.
  - Поля с персональными данными в телах запросов правило линтера `contracts/request-fields` разрешает только операциям из своего списка `allowedRequests`. В ответах их разрешает `contracts/pii-placement` — только операциям из списка `allowedResponses`. В v1 первый список — создание брони и вебхук брони, второй пуст.
  - Персональные данные допускаются только в тело с точным составом: у каждой операции из `allowedRequests` есть список полей в опции `fields` того же правила, иначе линтер падает при запуске. Обе опции — у одного правила, потому что правило Redocly видит только свои опции. Список обязателен и у вебхуков каналов, см. «[Каналы](#каналы)».
  - Список для операции «METHOD path» — поля всего дерева тела через `$ref`, `allOf`, `anyOf`, `oneOf` и `items`: имена свойств через точку, `[]` после имени массива. Лишнее поле и недостающее поле списка — ошибки. Тело со списком — только `application/json` со схемой. Объект без свойств, `additionalProperties` со схемой, булева схема `true` и схема, которая содержит саму себя, запрещены: они пропустили бы поля мимо списка. Новое поле — осознанная правка списка.
  - Список держит имена полей, а не их схемы. Ослабить шаблон или поднять `maxLength` у поля из списка линтер не мешает: в запросе это совместимое изменение. Схемы полей стережёт ревью.
  - Вне `allowedRequests` поле с персональными данными ищется по словарю имён:
    - частью имени — `email`, `phone`, части имени человека, в том числе `given_name` и `family_name`, паспорт, дата рождения, токен, номер и держатель карты, адрес, `mobile`, `msisdn`, `snils`, `tax_id`, `contact`, `comment`, `remark` и `special_requests`, а также имена на `guest`;
    - словом имени — `pan`, `inn`, `note`, `notes`, `dob` и `guest`. Имя делится на слова по `_` и `-` и перед заглавной буквой, с которой начинается слово, а заглавные подряд остаются одним словом: `X-Payer-INN` — это `x`, `payer` и `inn`. Частью имени эти короткие слова ловили бы чужие имена: `pan` — `company` и `time_span`, `inn` — `inner` и `dinner_included`, `note` — `refund_not_executed` и `footnote`, `dob` — `adobe_id`. Словом ловятся `card_pan`, `payer_inn`, `notes`, а `guest` — в любом месте имени: `lead_guest_name` и `primary_guest`. `guests` — число гостей, не персональные данные.

    ИНН и налоговый номер считаются персональными данными, даже если это номер юрлица. Если контракту понадобится номер компании, в словарь вносится явное исключение — как `guests`, — а поле не переименовывается в обход словаря. Словарь не бывает полным: имена вне него проверка пропускает. Тела операций из `allowedRequests` от этого защищает точный список. Словарь проверяется таблицей имён в `check.sh`, на каждое слово и на имена, где короткое слово стоит внутри длинного.
  - Имя свойства — ASCII snake_case, это проверяет `rule/property-name-snake-case`. Словарь сравнивает имена без символов вне `a-z` и `0-9`, поэтому `еmail` с кириллической «е» прошло бы мимо него. Имена заголовков ответа шаблоном не ограничены, и заголовок с такой буквой словарь пропустит.
  - Список для операции, которой нет ни в одном документе, линтер не замечает: правило видит один документ за раз.
- **Токен карты** — `tok_` и от 16 до 128 символов base64url. Цепочка из 12 и больше цифр — подряд или через `-` и `_` — запрещена, поэтому номер карты из 12–19 цифр за токен не пройдёт. Номер, записанный иначе — через буквы или в base64url, — шаблон не ловит. Префикс `tok_` — формат заглушки провайдера. С настоящим провайдером шаблон ослабят, а запрет цифр перенесут в новый шаблон.
- **Имя и фамилия** — без цифр: буквы, знаки ударения, пробел, дефис, апострофы `'` и `’`, точка. iOS по умолчанию заменяет `'` на `’`, поэтому разрешены оба. Это частичная мера: номер карты не ляжет в имя, но пройдёт в локальной части email и в телефоне — 15-значный номер является валидным E.164.
- Ответы с токеном брони или состоянием брони — 201, статус и отмена — идут с `Cache-Control: no-store`. Значение проверяется на директиву `no-store`: Symfony дописывает к ней `private`.
- Примеры в контрактах синтетические: email на `example.com`, вымышленные имена, телефон `+70000000000` — кода 000 у +7 нет. Токен брони в примерах — `bt_EXAMPLE…`. Поиск секретов должен исключать его по точному значению, а не по пути или шаблону, а в сидах и тестах он не используется.

### Доступ

- Схемы безопасности ([ADR-0007](../docs/adr/0007-access-and-authentication.md)):
  - `hotelApiKey` — ключ отеля `hk_…`, `http`, `bearer`;
  - `bookingToken` — токен брони `bt_…`, `http`, `bearer`;
  - `channelApiKey` — ключ канала `ck_…`, `http`, `bearer`. У операций вебхука ещё заголовки подписи `X-Timestamp` и `X-Signature`, см. «[Каналы](#каналы)»;
  - `serviceToken` — токен сервиса, `http`, `bearer`, `bearerFormat: JWT`. Описан только во внутреннем контракте;
  - `channelSyncKey` — ключ, который канал выдал channel-sync, `http`, `bearer`. Описан только в документе заглушки канала.
- У каждой операции `security` задан явно. Пустой — только у поиска и создания брони: гостю учётные данные не нужны.
- **`x-callers`** у внутренней операции — сервисы, которым её можно вызывать, по матрице вызовов ADR-0002. Вызывающий не из списка получает 403. Маршруты каждого сервиса с `security` и `x-callers` сверит тест в CI (ADR-0007), он появится вместе с сервисами.

### Порядок проверок

1. Маршрут: неверно оформленный id — 404.
2. Учётные данные — 401. Ответ зависит только от учётных данных, а не от существования ресурса. На маршрутах брони: нет заголовка `Authorization` — 401, любое другое значение, кроме подходящего токена, — 404.
3. Владение. Публичные операции — 404 на чужой и несуществующий ресурс. Внутренние — 403 по `x-callers`, затем `hotel_not_found`.
4. Схема — 422: формат, обязательные поля, пределы, соотношения полей вроде «выезд позже заезда».
5. У внутренних операций по брони — запись по id брони: `hotel_mismatch`, сохранённый результат, завершённое удержание или отметка «снято».
6. Проверки по данным и времени — 422: заезд в прошлом по дате отеля, горизонт, тип номера. Затем 409: наличие и сумма. На маршрутах брони 409 отдаётся только после совпавшего токена.

Запись по id идёт раньше проверок по дате, иначе повтор «удержать» после полуночи по времени отеля получил бы 422 «заезд в прошлом» вместо сохранённого снимка.

У создания брони первыми идут шаги ключа идемпотентности, см. ниже. У вебхуков каналов порядок свой, см. «[Каналы](#каналы)».

### Ключ идемпотентности

Создание брони требует заголовок `Idempotency-Key` (П-14 PRD).

- Ключ — UUID v4 или v7, который генерирует клиент, в любом регистре (RFC 9562, раздел 4). Сервер приводит его к нижнему регистру. Ключ должен быть случайным: ключи общие для всех гостей, и предсказуемый ключ может оказаться занят.
- Порядок шагов:
  1. Нет ключа — 400 `idempotency_key_missing`, ключ неверного формата — 422.
  2. Тело не `application/json` — 415.

     Эти проверки не смотрят в тело, поэтому идут до записи ключа.
  3. Ключ записывается и привязывается к отелю из пути и к байтам тела первого запроса на 24 часа. Другой отель или другое тело — 422 `idempotency_key_mismatch`. Запрос с этим ключом ещё идёт — 409 `request_in_progress`. Итог уже есть — повтор получает его, с исходным `trace_id`.
  4. Тело: не JSON — 400, не проходит схему — 422.
  5. «Удержать» в inventory. Дату отеля, горизонт, тип номера и сам отель (404) проверяет оно.
- Итоги под ключом — 201 и 409 `no_availability`, `amount_changed` и `hold_expired`.
- Не итоги — 400 и 422 тела, 404, 422 от inventory, 503 и другие 5xx. Повтор с тем же ключом и тем же телом выполняется заново; после 503 он продолжает то же удержание. Исправленный запрос отправляется с новым ключом.
- «То же тело» — то же байт в байт. Клиент, который при повторе заново сериализует JSON, тоже может получить `idempotency_key_mismatch`.
- Ответ без итога сразу освобождает аренду ключа: повтор с тем же телом выполняется заново и не получает 409 `request_in_progress`.
- На сервере: отель из пути хранится в записи ключа отдельным полем, отпечаток тела — HMAC-SHA-256 сырых байтов с секретом booking, рядом — `kid` секрета. Неистёкшая запись с неизвестным `kid` — 500: запись не перезаписывается, id брони в ней не меняется ([ADR-0004](../docs/adr/0004-booking-saga.md), [ADR-0007](../docs/adr/0007-access-and-authentication.md)).

## Ошибки

### Problem Details

Ошибки — в формате Problem Details (RFC 9457), `application/problem+json`. Схема — `schemas/problem-details.v1.json`: корневая схема открыта, у каждого типа в `$defs` своя закрытая схема. Каждый ответ с ошибкой в OpenAPI ссылается на свой тип.

- **`type`** — абсолютный URI на описание типа в этом файле: `https://github.com/Fox056/hotel-booking/blob/main/contracts/README.md#<тип>`. Заголовки каталога ниже совпадают с именами типов, поэтому ссылка открывает описание.
  - URI — идентификатор типа: клиент сравнивает именно его (RFC 9457, раздел 3.1.1). После v1 он не меняется, поэтому этот файл, его заголовки, репозиторий и аккаунт не переименовываются. Переименованное имя на GitHub может занять чужой, и по старым URI открылась бы его страница.
  - База URI в коде — одна константа в `platform`.
- **`title`** — постоянный текст на английском. У `about:blank` — название статуса HTTP из закрытого списка в схеме: текст исключения или значения из запроса в него не попадёт.
- **`status`** — код HTTP.
- **`trace_id`** — trace id из `traceparent`, 32 hex-символа ([ADR-0006](../docs/adr/0006-observability.md)). Гость или отель называет его поддержке.
  - Обязателен у типов сервиса и у `about:blank` тех кодов, которые отдаёт только сервис: 401, 415 и 503.
  - У `about:blank` кодов, которые отдаёт не только сервис, необязателен. 400, 403 и 500 отдаёт ещё и фронт, 404 — ещё и шлюз, 413, 414, 502 и 504 — только фронт. Фронт ставит `trace_id`, только если успел прочитать `traceparent`, шлюз — никогда.
- `detail` и `instance` в v1 не используются. Значений из запроса в ошибках нет.
- **`about:blank`** — у отказов без смысла сверх кода HTTP (RFC 9457, раздел 4.2.1): 400, кроме `idempotency_key_missing`, 401, 403, 404 публичных операций, 413, 414, 415, 500, 502, 503 и 504.

### Каталог типов

Свой тип — у отказов, которые клиент различает по смыслу. Все типы ниже несут `type`, `title`, `status` и `trace_id`; поля сверх них указаны отдельно.

#### validation_error

422, «Validation error». Запрос не прошёл проверку. Поле `errors` — от 1 до 50 элементов, в каждом:
- `pointer` — JSON Pointer в тело запроса из имён полей контракта и индексов массивов, пустая строка — всё тело; или `parameter` — имя параметра пути, строки запроса или заголовка, как в контракте;
- `code` — причина, см. «Коды ошибок валидации».

Значений из запроса нет. Исправленный запрос создания брони отправляется с новым ключом.

#### idempotency_key_missing

400, «Idempotency key missing». Создание брони пришло без заголовка `Idempotency-Key`.

#### idempotency_key_mismatch

422, «Idempotency key mismatch». Ключ уже привязан к другому отелю или другому телу. Повтор с тем же отелем и тем же телом законен.

#### request_in_progress

409, «Request in progress». Запрос с этим ключом ещё выполняется. Повторить позже с тем же ключом и телом.

#### no_availability

409, «No availability». Остатка не хватает хотя бы на одну ночь. Если вдобавок изменилась сумма, ответ всё равно этот.

#### amount_changed

409, «Amount changed». Сумма сервера не совпала с ожидаемой. Поле `current_amount` — текущая сумма в копейках.

#### hold_expired

409, «Hold expired». Повтор создания брони пришёл, когда удержание уже истекло или снято или до его срока меньше минуты. Брони нет, id брони в ответе нет; бронь создаётся заново с новым ключом.

#### cancellation_not_allowed

409, «Cancellation not allowed». Бронь нельзя отменить: момент заезда наступил, бронь ожидает оплаты или не подтверждена, или это бронь из канала. Сроки проверяются только у подтверждённой брони: повторная отмена уже отменённой всегда получает 200 с текущим состоянием.

#### offered_below_committed

409, «Offered below committed». Отель выставляет меньше номеров, чем продано и удержано, хотя бы на одну дату. Ничего не меняется. Поле `dates` — эти даты.

#### hold_finished

409, «Hold finished». Внутренний API. Удержание брони истекло, снято или его не было: второго удержания у брони не бывает. Booking переводит его гостю в `hold_expired`.

#### booking_released

409, «Booking released». Внутренний API. У брони стоит отметка «снято», поэтому запоздавшая продажа из канала отказывает.

#### hotel_not_found

404, «Hotel not found». Внутренний API. Отеля из пути нет. По этому типу вызывающий отличает ответ операции от 404 без типа, который бывает, когда маршрута нет.

#### hotel_mismatch

409, «Hotel mismatch». Внутренний API. Отель из пути не совпадает с отелем брони с этим id. Ничего не меняется.

### Коды ошибок валидации

Список открытый: незнакомый код клиент понимает как ошибку этого поля или параметра. Коды v1:

| Код | Когда |
|---|---|
| `required` | нет обязательного поля или параметра |
| `invalid_type` | значение другого типа |
| `invalid_format` | значение не отвечает формату или шаблону: дата, UUID, email, телефон, токен карты, `Idempotency-Key` |

| `unknown_property` | неизвестное поле в закрытом теле; `pointer` — родительский объект |
| `not_after_start` | конец диапазона не позже начала: дата выезда не позже даты заезда или `to` не позже `from` |

| `beyond_horizon` | ночи за горизонтом продаж |

### Что booking делает с ответом inventory

| Ответ inventory | «удержать», гость ждёт | «подтвердить» | «снять» | продажа из канала |
|---|---|---|---|---|
| успех | создание продолжается | бронь подтверждена | номера освобождены | продано, флаг овербукинга из ответа |
| 404 `hotel_not_found` | гостю 404 | отказ конфигурации | отказ конфигурации | отказ конфигурации |
| 409 `no_availability`, `amount_changed` | гостю тот же ответ | — | — | — |
| 409 `hold_finished` | гостю 409 `hold_expired` | «удержание не подтверждено», «снять» и возврат | — | — |
| 409 `booking_released` | — | — | — | шаг закончен: бронь уже отменена |
| 422 `validation_error` | гостю 422 с тем же `pointer` и `code` | — | — | окончательный отказ |
| 401, 403 | гостю 503, breaker считает | повтор | повтор | повтор |
| таймаут, ошибка соединения, 5xx | гостю 503, breaker считает | повтор | повтор | повтор |
| отказ конфигурации по ответу | гостю 503, breaker не считает | повтор | повтор | повтор |

- «—» значит, что у операции такого ответа нет; если он пришёл, это ответ вне контракта.
- **Отказ конфигурации по ответу внутреннего API** — `hotel_mismatch`, 404 `hotel_not_found` у фоновых шагов, 400, 413 и 415, а также ответ вне контракта: код HTTP или `type`, которых нет у операции, 404 без типа, 422 с `pointer` вне общих полей или с `parameter`. Такой ответ говорит о расхождении версий или ошибке, а не об ответе по существу ([ADR-0007](../docs/adr/0007-access-and-authentication.md)).
- **Повтор** — как при недоступном получателе, в пределах бюджета шага ([ADR-0003](../docs/adr/0003-sync-and-async-interactions.md)).
- **Breaker** — только у гостевого пути; фоновые шаги его не читают и не считают. Отказ конфигурации по ответу breaker не считает: такой ответ гость может вызвать своим вводом, если booking и inventory проверяют его по-разному.
- Новое поле в успешном ответе — не ответ вне контракта.

## Ответы фронта и шлюза

Это общие компоненты `common.v1.yaml`, они перечислены у каждой операции.

- **Публичные операции:**
  - всегда — 400, 414, 500, 502, 503 и 504; у операций с телом — ещё 413 и 415;
  - 429 — лимит шлюза: обычный текст с обязательным `Retry-After`;
  - `Content-Type: text/plain` у 429, 502 и 504 шлюза ставит middleware `contentType`, первым в цепочке публичных роутеров. Точка входа Traefik отключает автоопределение типа (`contenttype.DisableAutoDetection`), и без этого middleware такие ответы ушли бы без `Content-Type`;
  - у 502 и 504 два медиатипа: Problem Details фронта и обычный текст шлюза. У 503 — Problem Details сервиса и обычный текст шлюза: сам фронт 503 не отдаёт;
  - `Retry-After` у 503 необязателен: у текстового 503 шлюза его нет. 503 сервиса его несёт всегда.
- **Вебхуки каналов** — как публичные операции, но без 429: шлюз их не ограничивает, а на 4xx канал доставку не повторит ([ADR-0007](../docs/adr/0007-access-and-authentication.md)). Их набор ответов — в «[Каналы](#каналы)».
- **Внутренние операции** — те же коды, кроме 429, и только Problem Details: вызов идёт по сети пары, мимо шлюза. `Retry-After` у 503 обязателен.
- **404 «нет маршрута»** шлюз отдаёт со статического сервера страниц ошибок, на любой метод, в Problem Details без `trace_id` (компонент `RouteNotFound`). К операциям он не привязан.
- **Свои ответы фронта** (nginx): 400, 403, 404, 405, 411, 413, 414, 494, 500, 501, 502 и 504 — Problem Details. 494 «заголовки слишком большие» клиент получает как 400. Свой 404 nginx отдаёт только на путях вне операций, например на прямой запрос к своим страницам ошибок. Ответа 408 нет: на таймаут nginx закрывает соединение.

### Ответы на неверно оформленный или чрезмерный запрос

К операциям они не привязаны: исправный клиент их не получает.

| Кто | Код | Тело | Когда |
|---|---|---|---|
| шлюз | 400, 501, 505 | обычный текст или пустое тело | HTTP-запрос оформлен неверно. Отвечает Go-сервер Traefik при разборе запроса (`conn.serve`, Go 1.26) или обработчики точки входа Traefik 3.7.16: `denyOpaque` и `denyFragment` — 400, `denyConnect` — 501 на CONNECT, у них тело пустое |
| шлюз | 431 | обычный текст по HTTP/1.x, HTML по HTTP/2 | заголовки больше предела. По HTTP/1.x — `maxHeaderBytes` (в Traefik 3.7.16 — 1 МиБ) плюс 4 КиБ запаса (`Server.initialReadLimitSize`). По HTTP/2 — `maxHeaderBytes` плюс 320 байт, и каждое поле считается как имя, значение и 32 байта (`http2adjustHTTP1MaxHeaderSize`); ответ пишет `http2handleHeaderListTooLong`, медиатип определяется по содержимому. Всё — Go 1.26 |
| фронт | 405, 411, 501 | Problem Details | метод, длина или кодирование тела, которые nginx не принимает |

## Каналы

Каналы продаж присылают брони и отмены вебхуками в channel-sync — `openapi/channel-sync.v1.yaml`. channel-sync отправляет в канал остатки и цены — `openapi/channel-stub.v1.yaml`. Доступ устроен по [ADR-0007](../docs/adr/0007-access-and-authentication.md), поведение — по К-1, К-2 и К-3 PRD.

### Вебхуки

**Маршруты:**
- `POST /v1/channels/{channel_id}/hotels/{hotel_id}/bookings` — бронь;
- `POST /v1/channels/{channel_id}/hotels/{hotel_id}/cancellations` — отмена.

Канал и отель — в пути, внешний id брони — в теле, строки запроса нет. Вид вебхука задаёт маршрут, а путь входит в подпись. Поэтому тело брони нельзя переслать на маршрут отмены, другому отелю или каналу. Канал из пути сверяется с ключом: канал A не пришлёт вебхук от имени канала B.

На стенде вебхуки шлют только заглушки каналов, через свою точку входа шлюза. В продакшене роутер каждого канала открыт только его адресам — условием `ClientIP`, а чужой адрес получает обычный 404 «нет маршрута» ([ADR-0007](../docs/adr/0007-access-and-authentication.md)).

Запросы под `/v1/channels/`, которые не совпали ни с одним роутером канала, — чужой адрес или чужой канал в пути — ловит запасной роутер:
- он отвечает тем же 404, что и «нет маршрута», поэтому код канала не раскрывается;
- его ответы считает алерт с порогом за окно: так видна потеря броней канала, который сменил адреса или ошибся в пути. Порог нужен, потому что сюда же попадают сканеры.

Поэтому в продакшене чужой канал в пути обычно получает 404 шлюза, а не 403. 403 «канал в пути не совпадает с ключом» остаётся на стенде и там, где адреса двух каналов пересекаются, например при общем выходе через NAT. Его тоже считает алерт.

**Подпись.**
- `Authorization: Bearer ck_…` — ключ канала.
- `X-Timestamp` — время подписи: Unix-время в секундах, ровно 10 цифр. Оно расходится с часами channel-sync не больше чем на 300 с в любую сторону.
- `X-Signature: v1=<hex>` — HMAC-SHA256 от строки подписи: 64 hex-символа в нижнем регистре.
- Строка подписи — `{метод}\n{путь}\n{метка}\n{тело}`, где `\n` — байт 0x0A:
  - метод — `POST`;
  - путь — сырой request-target до `?`, байт в байт, без схемы и хоста; сервис берёт его из `REQUEST_URI`;
  - метка — значение `X-Timestamp` как есть;
  - тело — байты тела как отправлены.

  Строка однозначна: в методе и пути не бывает перевода строки, в метке только цифры, тело последнее.
- Ключ HMAC — 32 байта секрета канала. Текст секрета — `cs_` и 43 символа base64url без `=` ([ADR-0007](../docs/adr/0007-access-and-authentication.md)). Ключом служат декодированные байты, а не текст.
- Каждую попытку доставки канал подписывает заново, со свежей меткой. Повтор с исходной меткой позже чем через 300 с получил бы 401, а 401 канал не повторяет.
- Хост в подпись не входит, поэтому секреты каналов у каждого окружения свои.
- channel-sync пробует каждый действующий секрет канала — на время ротации их два — и сравнивает подпись за постоянное время.

**Тестовый вектор.** Реализации подписи у channel-sync и у заглушек проверяют себя на нём.

| Что | Значение |
|---|---|
| секрет | `cs_EXAMPLEchannelHmacSecretNotRealDoNotUse0000` |
| ключ HMAC, hex | `11700c3cb11c85a9e77a51e669c49e72b7ad368b5179a943a0da2d52c7b4d34d` |
| метод | `POST` |
| путь | `/v1/channels/ota-example/hotels/0190f5c8-7c6e-7a3b-9f1e-2b3c4d5e6f70/bookings` |
| `X-Timestamp` | `1793869200` — 2026-11-05T09:00:00Z |
| тело, 252 байта UTF-8 | `{"external_id":"EXAMPLE1234567890","room_types":[{"room_type_code":"DBL-STD","rooms":1}],"check_in_date":"2026-11-10","check_out_date":"2026-11-12","guests":2,"guest":{"first_name":"Пример","last_name":"Гостев","email":"guest@example.com"}}` |
| строка подписи | `POST\n/v1/channels/ota-example/hotels/0190f5c8-7c6e-7a3b-9f1e-2b3c4d5e6f70/bookings\n1793869200\n` и тело — 346 байт |
| `X-Signature` | `v1=5b1a74132c1351020574f1b7ce371b1b5240f9965ec90f796a8ffe41c37ac684` |

- Если ключом взять весь текст секрета `cs_…` в UTF-8, получится `v1=bb2e3925…` — это частая ошибка.
- Разбор файла секрета строгий: `cs_` и ровно 43 символа base64url в канонической кодировке — два младших бита последнего символа нулевые. После декодирования — 32 байта. Иначе сервис не стартует.
  - Нестрогий декодер отбросил бы лишние биты, и тексты `…Use0001`–`…Use0003` дали бы тот же ключ, что у вектора.
  - `sodium_base642bin` с `SODIUM_BASE64_VARIANT_URLSAFE_NO_PADDING` такие тексты отвергает сам.
- Секрет вектора помечен `EXAMPLE`. Генерация секретов его не выдаёт, а поиск секретов исключает его по точному значению, как `bt_EXAMPLE…`. Сервис с ним не стартует: запрет сравнивает декодированные байты с ключом вектора, а не текст.

**Порядок проверок.**
1. Фронт, до сервиса: тело больше 1 МиБ — 413, слишком длинная стартовая строка — 414, неверно оформленный запрос — 400. Повтор `Authorization` тоже даёт 400: nginx 1.28 разбирает этот заголовок как уникальный (`ngx_http_process_unique_header_line`).
2. Маршрут — 404: неверно оформленный `channel_id` или `hotel_id`, `%` в пути. Сегменты пути проверяются до декодирования, чтобы маршрут и подписанная строка совпадали при любом декодировании в шлюзе и фреймворке. Символы вне маршрута — 404 шлюза.
3. Учётные данные — 401 без побочных эффектов:
   - ключа нет, или он неверный;
   - метки нет, она неверно оформлена или вне окна;
   - подписи нет, она неверно оформлена или не сходится;
   - есть строка запроса, даже пустая `?`.

   Повтор `X-Timestamp` или `X-Signature` — тоже 401: nginx 1.28 склеивает одноимённые заголовки через «, » (`ngx_http_fastcgi_create_request`), и склеенное значение не проходит формат.

   Сначала проверяется ключ, затем метка, затем подпись. HMAC от тела до 1 МиБ считается, только когда ключ найден, а метка в окне.
4. Доступ — 403: канал в пути не совпадает с ключом; отель не подключён к каналу или не существует. Ответ эти случаи не различает, а алерт различает их по причине. В продакшене чужой канал в пути обычно получает 404 шлюза, см. выше.
5. Лимит канала — 503 с `Retry-After` не больше 60 с. Квоту расходуют только запросы, которые прошли шаги 2–4.
6. Тело:
   - `Content-Type` не `application/json` или есть `Content-Encoding` со значением, отличным от одного `identity` без учёта регистра, — 415. Список кодирований, даже `identity, gzip`, тоже 415. Подпись считается от байтов, которые пришли, поэтому сжатого тела нет;
   - тип и `charset` сравниваются без учёта регистра, `charset` бывает только `utf-8` и может быть в кавычках, остальные параметры не учитываются: `application/json; charset=UTF-8` проходит;
   - тело не JSON — 400;
   - тело не объект JSON, `external_id` нет или он неверно оформлен — 422.
7. Вебхук записан — 202.

**Ответы и что делает канал.**

| Код | Когда | Канал |
|---|---|---|
| 202 | вебхук записан: бронь, отмена, дубль или запись на ручной разбор | доставка закончена |
| 400, 404, 415, 422 | запрос нельзя опознать | не повторяет, срабатывает алерт |
| 405, 411, 414 | фронт не принял запрос | не повторяет, срабатывает алерт |
| 401 | учётные данные не подошли | не повторяет, срабатывает алерт |
| 403 | канал или отель в пути не подходят | не повторяет, срабатывает алерт |
| 413 | тело больше 1 МиБ | не повторяет; только метрика: это защита от мусора, а не предел брони |
| 503 | лимит канала, или channel-sync не может записать вебхук | повторяет после `Retry-After`, подписав заново |
| 500, 502, 504, таймаут | сбой | повторяет, подписав заново |

- 429 у вебхуков нет: шлюз их не ограничивает.
- Из-за содержимого запроса 4xx бывает, только когда запрос нельзя опознать — 400, 404, 415 и 422. Это осознанное исключение из правила «бронь из канала не отбрасывается»: без внешнего id брони дубли не отсечь.
- Любой 4xx на вебхук, кроме 403 со своим алертом и 413 — защиты от мусора, считает алерт ([ADR-0006](../docs/adr/0006-observability.md)). Канал такой ответ не повторяет, и бронь теряется.

**Дубли.**
- Внешний id уникален в пределах канала — во всех его отелях. Набор его символов сверяется с каналом при подключении: иначе брони канала получат 422.
- Ключ — канал, внешний id и вид вебхука (П-14 PRD). Запись хранит ещё отель из пути.
- Тот же ключ и тот же отель — дубль: 202, ничего не меняется. Тело не сравнивается: изменение брони вне рамок, первая версия остаётся. Как заметить изменённую бронь, которую канал прислал повтором, — открытый вопрос В-10 в [реестре рисков](../docs/risks.md).
- Тот же ключ и другой отель нарушают уникальность внешнего id: 202, запись уходит на ручной разбор с алертом.
  - У брони в записи — поля из разрешённого списка, у отмены — только ключ и отель.
  - Повторы такого вебхука — дубли этой записи по ключу с отелем: второй записи и второго алерта нет.
- Отмена применяется только к брони с тем же каналом, внешним id и отелем из пути. Ответ — 202, нашлась бронь или нет.

**Тело и что из него сохраняется.**
- Тело открыто на всех уровнях: незнакомые поля игнорируются и не сохраняются.
- Разрешённый список — свойства схем тела. Его держит правило `contracts/request-fields`: оно сверяет поля всего дерева тела — со вложенными схемами, ветками и ссылками — со списком операции вебхука, см. «[Персональные данные и токены](#персональные-данные-и-токены)».
- В запись о вебхуке, в запись на ручном разборе и в команду в booking попадают только поля из разрешённого списка. Из них — только значения, которые прошли схему своего поля.
- Вместо неверного значения хранятся `pointer` и `code` — без значения. Текст ошибки проверки со значением не сохраняется и не пишется в лог. Так номер карты в фамилии или поле на сотни килобайт в базу не попадут.
- Записи, логи и алерты ссылаются на внутренний id записи, а не на внешний id брони: это косвенный идентификатор гостя ([ADR-0006](../docs/adr/0006-observability.md)).

**Поля брони.**

| Группа | Поля | Если значения нет или оно не отвечает схеме |
|---|---|---|
| опознание | `external_id` | 422 |
| продажа | `room_types`, `check_in_date`, `check_out_date` | 202, бронь ждёт ручного разбора |
| данные гостя | `guests`, `guest` и его поля | 202, поле не сохраняется, бронь идёт дальше |

- На ручной разбор уходит и бронь, у которой код типа номера не сопоставлен, в `room_types` больше одного элемента или повтор кода, даты не по порядку или ночи за горизонтом продаж (К-2).
- Заезд в прошлом допустим (П-11).
- Данные гостя на разбор не отправляют. Неверное значение по правилам выше и так не сохраняется. А запись на разборе не уменьшает наличие, и номер успели бы продать снова.
- Отброшенные поля данных гостя считает метрика по каналу и полю. Метка поля — из закрытого набора `guest`, `guests`, `first_name`, `last_name`, `email`, `phone`, без указателя и значения. `guest` — когда сам объект гостя не прошёл схему.

**Пределы и 256 КиБ.** Команда в booking должна помещаться в строку outbox — 256 КиБ ([ADR-0005](../docs/adr/0005-outbox-and-inbox.md)).
- Команду строит только бронь с одним типом номера. Вместо кода канала команда несёт `room_type_id`.
- Строки брони в сумме — 682 символа: `external_id` 128, `room_type_code` 64, имя и фамилия по 100, email 254, телефон 16, две даты по 10.
- Даже если каждый символ займёт в JSON 12 байт (`\uXXXX\uXXXX`), это меньше 8 КиБ, а с конвертом — меньше 16 КиБ.
- Запись на разборе ограничена теми же пределами: неверные значения в неё не попадают.

**Метрики и принятый риск.**
- Метку канала у метрик вебхука берут из найденного ключа, а не из пути: до проверки ключа в пути что угодно. Неизвестный ключ — `other`.
- Перехваченный вебхук можно повторять, пока метка в окне. Это дубль, но он расходует квоту канала, и настоящие вебхуки получат 503. Брони не теряются: канал повторит доставку. Риск принят.

### Протокол заглушек каналов

`openapi/channel-stub.v1.yaml` — API канала, которое реализуют заглушки из `fake-externals`. У настоящего канала свой протокол, и channel-sync переводит его в свою модель отдельно для каждого канала (раздел 4 PRD).

- `POST /v1/hotels/{hotel_id}/availability` — абсолютные остаток и цена по парам «тип номера, дата», от 1 до 1000 пар за вызов. Меняются только перечисленные пары, поэтому POST, а не PUT. Повтор безопасен.
- Отель — наш id, тип номера — код канала `room_type_code` по сопоставлению.
- Пара встречается в вызове один раз.
- Без `price` дата не продаётся, и прежнюю цену канал не оставляет — как в событии наличия.
- Доступ — `channelSyncKey`: ключ, который канал выдал channel-sync, в `Authorization: Bearer`. Это отдельный секрет — не `ck_` и не секрет HMAC. Формат задаёт канал. Ключ заглушек создаёт генерация секретов, а поиск маркеров ищет его по точному значению.

| Ответ канала | Что делает channel-sync (К-1 PRD, [ADR-0003](../docs/adr/0003-sync-and-async-interactions.md)) |
|---|---|
| 204 | обновляет состояние канала |
| 429 с `Retry-After` | ждёт и повторяет |
| любой 5xx, таймаут 5 с | повторяет с backoff; у 503 `Retry-After` необязателен |
| любой другой 4xx, 3xx | не повторяет: сообщение уходит в DLQ, срабатывает алерт |

- `Retry-After` — целые секунды от 0 до 86400. Значение вне контракта — дата, отрицательное или больше предела — считается отсутствующим, и работает backoff.
- Время следующей попытки хранится в состоянии канала в базе, без ожидания в процессе ([ADR-0003](../docs/adr/0003-sync-and-async-interactions.md)). Канал, который надолго просит ждать, виден по алерту на задержку синхронизации.
- Перенаправления не выполняются ([ADR-0007](../docs/adr/0007-access-and-authentication.md)). Тела ответов channel-sync не читает, и у ошибок заглушки тела нет.
- API управления заглушкой — сбои, задержки, чтение принятого — не контракт сервисов: его задаёт сама заглушка.

Документ помечен `x-implemented-by: fake-externals`: это API внешней системы, шлюз его не публикует. Нашего фронта и шлюза у внешней системы нет. Поэтому в `redocly.yaml`, в `apis` для этого документа, выключены три правила нашего API: `rule/public-response-set`, `contracts/error-media-types` и `contracts/unauthorized-shape`. Остальные правила действуют: пределы, подмножество OpenAPI, форма ссылок, закрытые ответы, `Retry-After` у 429, место персональных данных.

## Сообщения

События Kafka описывает `asyncapi/events.v1.yaml`, схемы сообщений лежат в `schemas/`. У команд RabbitMQ тот же конверт.

### Конверт

Тело сообщения — объект JSON, конверт (`schemas/envelope.v1.json`):

| Поле | Что это | У кого |
|---|---|---|
| `message_id` | UUID v7 в нижнем регистре — id строки outbox. При повторной отправке не меняется | у всех |
| `type` | тип сообщения `<область>.<имя>.v<N>`, например `booking.state.v1`. У события область — имя топика без версии | у всех |
| `created_at` | время создания строки outbox в UTC с миллисекундами: `YYYY-MM-DDThh:mm:ss.sssZ` | у всех |
| `headers` | межсервисные заголовки: `traceparent`, а у команд с персональными данными ещё `pii_retain_until` | необязательно |
| `version` | версия ключа: `epoch` и `number` | у событий compacted-топиков |
| `change_id` | id изменения издателя, общий у сообщений одного изменения | у событий наличия |
| `payload` | данные типа | у всех |

- Общая форма — `envelope.v1.json#/$defs/Envelope`, она открыта: на неё опирается получатель. У каждого типа своя закрытая схема в файле его топика, поля конверта в ней — ссылки на определения `envelope.v1.json`. Закрытую схему проверяют тесты издателя, как схемы ответов.
- `created_at` — исключение из правила «моменты без долей секунды». По нему считаются задержка до каналов и отставание потребителей ([ADR-0006](../docs/adr/0006-observability.md)), и секунды завышали бы задержку до целой секунды. Время усекается до миллисекунд один раз, при создании строки outbox: колонка строки и конверт берут одно значение, а свойство `timestamp` RabbitMQ — его целые секунды.
- `pii_retain_until` — срок хранения персональных данных сообщения, без долей секунды. Все копии сообщения стирают их по раннему из этого срока и 30 дней от `created_at` ([ADR-0005](../docs/adr/0005-outbox-and-inbox.md)). У событий этого заголовка нет: персональных данных в них нет.
- Заголовки конверта — только межсервисные, из списка контракта. Служебные данные Messenger — штампы шины, повторов и ошибок — сериализатор `platform` хранит в заголовках транспорта очередей в базе и failure transport, вне конверта ([ADR-0001](../docs/adr/0001-monorepo-and-structure.md), [ADR-0007](../docs/adr/0007-access-and-authentication.md)).
- Конверт собирает `platform` при записи строки outbox, тело строки — весь конверт. Relay отправляет его как есть.
- В RabbitMQ тело — тот же конверт, и оно источник правды. Копия конверта для брокера и инструментов, которые не разбирают тело:
  - свойства `message_id` и `type`;
  - свойство `timestamp` — секунды POSIX, `created_at` с отброшенными миллисекундами;
  - заголовки AMQP `traceparent` и `pii_retain_until`.

  Получатель сверяет копию с конвертом: при расхождении сообщение не разобрано. Заголовки `x-*` брокера и заголовок инструмента разбора в конверт не входят и не сверяются.

### Получатель

- Получатель проверяет сообщение по общей форме и по тем полям, которые ему нужны, но не по закрытой схеме типа: иначе новое необязательное поле сломало бы его.
- Незнакомые поля на любой глубине — в конверте, заголовках и `payload` — получатель игнорирует.
- Отсутствующий или неверный `traceparent` сообщение не портит: обработка начинает новый трейс ([ADR-0006](../docs/adr/0006-observability.md)). Неверное значение отбрасывается целиком: оно не попадает ни в логи, ни в атрибуты и ссылки спанов и не разбирается по частям.
- Персональные данные сообщения получатель не хранит и не использует после `pii_retain_until`, даже если сообщение пришло позже этого срока.
- Сообщение не разобрано ([ADR-0005](../docs/adr/0005-outbox-and-inbox.md)), если:
  - в нём нет `message_id`, `type`, `created_at` или `payload`;
  - `created_at` больше чем на час в будущем. По `created_at` считаются окно inbox, сроки хранения и задержки, и время из будущего держало бы сообщение дольше срока;
  - тип не из типов этого топика или этой очереди;
  - ключ записи Kafka не совпадает с ключом, собранным из `payload`;
  - у записи Kafka нет значения.

  Из RabbitMQ такое сообщение уходит в очередь разбора, из Kafka — в отложенные, с алертом.
- Получатель применяет событие, только если его версия старше сохранённой: сначала сравнивается эпоха, затем номер. Равная версия — дубль, младшая — устаревшее событие.
- Событие compacted-топика несёт полное состояние ключа. Нет поля — нет значения: например, без `price` у даты нет цены, и получатель не оставляет прежнюю.
- Получатель не ждёт всех сообщений одного изменения: младшую версию ключа relay не отправляет, если в той же пачке есть старшая ([ADR-0005](../docs/adr/0005-outbox-and-inbox.md)).

### Kafka

| Топик | Ключ | Типы | Партиций | Очистка | Хранение | Издатель | Группы потребителей |
|---|---|---|---|---|---|---|---|
| `availability.v1` | `{hotel_id}:{room_type_id}:{date}` | `availability.state.v1` | 12 | `compact,delete`, compaction не раньше 7 дней | 400 дней | inventory | channel-sync |
| `booking.v1` | `{hotel_id}:{booking_id}` | `booking.state.v1` | 6 | `compact,delete`, compaction не раньше 7 дней | 400 дней | booking | payment |
| `payment.v1` | `{hotel_id}:{booking_id}` | `payment.charged.v1`, `payment.refunded.v1` | 3 | `delete` | 7 дней | payment | — |

- Ключ — строка UTF-8 только из id и дат: сначала отель, затем через двоеточие другие UUID или даты. Шаблон ключа проверяет правило линтера, поэтому в ключе не может оказаться свободного текста. Двоеточия нет ни в UUID, ни в дате, поэтому ключ однозначен: compaction сравнивает байты ключа.
- Значение — конверт в JSON. Заголовков у записи нет, записей без значения в v1 нет.
- Время записи — время отправки, а не `created_at`: на нём держатся сроки хранения и задержка compaction.
- Числа партиций, сроки и задержка compaction обоснованы в [ADR-0003](../docs/adr/0003-sync-and-async-interactions.md). Число копий задаёт развёртывание.
- Адрес канала — это топик: имена в snake_case через точку и `.v<N>`, без параметров. Параметр адреса мог бы занести персональные данные в имя топика, а его видно в журналах брокера и метках метрик.
- В документе AsyncAPI у каждого топика один канал и ровно одна операция `send` — издатель — и операции `receive` потребителей. `x-service` — сервис операции из списка сервисов, а `groupId` у `receive` — имя его сервиса ([ADR-0002](../docs/adr/0002-service-boundaries-and-data-ownership.md)). По ним развёртывание создаёт топики и права, поэтому всё это проверяет правило линтера `contracts/event-access`.
- Каждая операция документа идёт через канал из корневого `channels` и его сообщения, у операций топиков нет ни `traits`, ни `reply`: правила событий и проверка примеров видят только корневые каналы, а трейт мог бы поменять привязки операции.
- `cleanup.policy` в документе — массив, как в биндингах Kafka 0.5.0.
- Правила событий действуют на канал, если среди его серверов есть Kafka, если сервер неизвестен или если серверов нет. Не действуют они, только если все серверы канала известны и работают по `amqp` или `amqps`, а привязки Kafka нет ни у канала, ни у его сообщений, операций, их трейтов и серверов. Пустой список серверов, как в AsyncAPI 3, значит «все серверы документа».

### События

- `availability.state.v1` — наличие и цена типа номера на дату, как `AvailabilityDay` публичного API: выставлено, продано, удержано, остаток, превышение и цена. Изменение на диапазон дат — событие на каждую дату с общим `change_id`.
- `booking.state.v1` — публичное состояние брони: статус и причина, статус возврата и признак `payment_outcome_unresolved` — исход оплаты не выяснен. Подсостояний саги и персональных данных нет ([ADR-0004](../docs/adr/0004-booking-saga.md)). Статусы, причины и статусы возврата — те же схемы, что в API брони.
- `payment.charged.v1` — деньги списаны. Публикуется один раз на бронь, когда payment впервые узнал о списании: из ответа провайдера, запроса статуса или сверки.
- `payment.refunded.v1` — возврат выполнен, с номером попытки.

Отказы и «исход неизвестен» в `payment.v1` не публикуются: деньги не двигались, а статус брони есть в `booking.v1`. «Чек отправлен» — событие заглушки провайдера, в `payment.v1` его нет.

Версия ключа:
- `number` растёт при каждом изменении ключа в базе владельца и при повторной публикации ключа.
- `epoch` растёт после восстановления базы владельца из резервной копии. Владелец публикует полный снимок новой эпохи, и его события побеждают старые события тех же ключей. Ключи, которых нет в снимке, — данные, потерянные при восстановлении, — остаются в топике со старой эпохой до конца срока хранения. Поэтому, пока они там, копии перестраиваются из выгрузки владельца, а не из топика ([ADR-0002](../docs/adr/0002-service-boundaries-and-data-ownership.md), [ADR-0003](../docs/adr/0003-sync-and-async-interactions.md)).
- `change_id` у повторной публикации ключа новый на каждый запуск, у полного снимка после восстановления — один на запуск.

### Версии и совместимость сообщений

- Основная версия — в имени топика и типа: `availability.v1`, `availability.state.v1`.
- Внутри v1 изменение допустимо, только если старый код читает новые сообщения, а новый — старые ([ADR-0001](../docs/adr/0001-monorepo-and-structure.md)). Топик хранит события до 400 дней ([ADR-0003](../docs/adr/0003-sync-and-async-interactions.md)), outbox, DLQ и отложенные — до 30 дней ([ADR-0005](../docs/adr/0005-outbox-and-inbox.md)).
- Совместимо:
  - новое необязательное поле в закрытой схеме: в `payload`, в конверте типа или в его заголовках — сначала в контракте, потом в коде;
  - новое определение в `$defs`, новый файл схем;
  - новый топик;
  - новый тип в топике без compaction — сначала потребители, потом издатель: незнакомое сообщение уходит в отложенные;
  - описания;
  - рост срока хранения `retention.ms`, кроме перехода на −1.
- Ломает:
  - удалить или переименовать поле, сделать его обязательным или необязательным;
  - описать новое поле в открытой схеме — в общей форме конверта или в корне Problem Details. Описанное поле сужает то, что схема принимает, а получатель проверяет сообщение именно по общей форме. Например, `traceparent`, описанный в общей форме, отклонил бы сообщение с неверным заголовком, а такое сообщение получатель обязан принять, см. «Получатель»;
  - поменять тип, формат, шаблон, пределы или значения перечисления. Перечисления в сообщениях закрыты: незнакомое значение старый потребитель не поймёт;
  - поменять ключ, число партиций, политику очистки или задержку compaction;
  - добавить в compacted-топик новый тип или записи без значения. Compaction оставляет у ключа одну запись, какого бы типа она ни была, и новый тип вытеснил бы полное состояние ключа;
  - уменьшить срок хранения: перестройка копии из топика рассчитывает на срок не меньше горизонта продаж. Переход на −1, то есть без срока, тоже ломает: у `[compact, delete]` это смена политики очистки.
- Схемы полей, на которые ссылается схема сообщения, — из `common.v1.yaml`, `inventory.v1.yaml` и `booking.v1.yaml` — меняются по этим же правилам. Ослабить шаблон поля запроса для HTTP совместимо, а для сообщения — нет.
- Версия 2 — новый топик `x.v2` и тип `x.y.v2`:
  1. Издатель пишет v1 и v2 в одной транзакции. В compacted-топик v2 он сначала публикует полный снимок.
  2. Потребители переходят на v2.
  3. В v1 перестают писать и удаляют его после срока хранения.

Эти правила проверяет `bin/compat.sh`, см. «Проверка»:
- `schemas/*.json` сравниваются напрямую, файл с файлом, в том числе конверт и Problem Details. Определения и поля сопоставляются по именам, `$ref` сравнивается как строка. Ссылку внутри файла отдельно проверять не нужно: каждое определение сравнивается на своём месте. Ссылки на `openapi/*.yaml` проверка разворачивает только в сообщениях: схему OpenAPI, на которую ссылается определение вне сообщений, она по правилам сообщений не сравнивает.
- `asyncapi/*.yaml` сравниваются документ с документом после `redocly bundle --dereferenced`:
  - каналы и сообщения сопоставляются по ключам документа, а `address` и `name` сравниваются как поля;
  - новый канал Kafka, чей топик в базе уже описан — под другим ключом или в другом документе, — не новый топик: для него действуют правила этого топика, и проверка считает такой канал изменением;
  - у канала сравниваются сообщения, настройки топика и описания, у сообщения — схема вместе со схемами полей из OpenAPI, ключ записи, заголовки, тип содержимого (свой или `defaultContentType` документа) и описания;
  - `info`, `servers` документа и каналов и `operations` не сравниваются: это развёртывание и доступ, их держат правила линтера. `components` тоже не сравниваются: сборка подставляет их в сообщения, и там они сравниваются;
  - документы OpenAPI сами по себе тоже не сравниваются: у API свои правила, см. «Совместимость».
- Совместимы только изменения из списка выше:
  - закрытой считается схема, у которой `additionalProperties: false` и в базе, и в изменении;
  - описания — это `description`, `title`, `summary`, `$comment`, примеры, `externalDocs`, `deprecated` и `tags`;
  - порядок значений в `required`, `enum` и `cleanup.policy` не важен;
  - любое другое изменение, например `$schema`, `default`, `readOnly` или `bindingVersion`, проверка считает ломающим.
- Изменение схемы сообщения видно дважды: в файле схем и в собранном документе. Схема поля из OpenAPI, на которую ссылаются несколько сообщений, после сборки входит в каждое из них. Поэтому одна её правка даёт по находке на каждое сообщение — это ожидаемо, а не ошибка проверки.
- Смысл поля проверка не видит: изменённое описание она считает совместимым, а смену смысла ловит ревью.

### Персональные данные в событиях

В событиях нет персональных данных и косвенных идентификаторов гостя — внешнего id брони канала и токена брони. Топики хранятся дольше срока обезличивания, а удалить запись из топика точечно нельзя ([ADR-0002](../docs/adr/0002-service-boundaries-and-data-ownership.md), [ADR-0003](../docs/adr/0003-sync-and-async-interactions.md)).

- Имя каждого поля события на любой глубине должно быть в разрешённом списке правила `contracts/event-fields` в `redocly.yaml`. Списков два: для конверта и его заголовков и для `payload`, поэтому имя конверта, например `number`, не вернётся внутри `payload`. Новое поле события — осознанная правка списка.
- Строка в `payload` — перечисление или значение формата `uuid`, `date` или `date-time`. Свободный текст мог бы нести персональные данные под любым разрешённым именем.
- Имена персональных данных и токена брони правило отклоняет, даже если их внесли в список. Так же оно отклоняет косвенные идентификаторы гостя, следы карты и заметки: имена с `external`, `reservation`, `confirmation`, `pnr`, `token`, `card`, `last4`, `maskedpan`, `comment`, `note` и имена `ip` и `name`. Имена в списках — только латиница в snake_case, иначе похожая буква провела бы запрещённое имя.
- Схемы событий закрыты на всех уровнях, поэтому тест издателя поймает лишнее поле. У сообщения события нет ни заголовков записи, ни `traits`: всё лежит в конверте.

## Подмножество OpenAPI 3.1

Ответы сервисов в тестах проверяются по контракту валидатором `league/openapi-psr7-validator` 0.24 на `devizzent/cebe-php-openapi` 1.1.5. Официально он поддерживает OpenAPI 3.0.x, поэтому контракты пишутся синтаксисом 3.1, но с семантикой 3.0. Подмножество держат правила линтера.

Схемы сообщений пишутся в том же подмножестве: сервисы проверяют сообщения тем же валидатором, и схемы событий ссылаются на компоненты OpenAPI. Для документов AsyncAPI есть два отличия:
- документ ссылается на фрагменты `#/$defs/…` JSON-файлов, а не на их корень: Redocly 2.60.0 проверяет схемы AsyncAPI по типам draft-07, где `$defs` нет;
- локальные `$ref` правило формы ссылок не ограничивает: куда они ведут, задаёт AsyncAPI 3.

- Без `const`: вместо него `enum` из одного значения.
- Без соседей у `$ref`: league их молча игнорирует. Нужны соседи — `allOf`.
- Без `unevaluated*`, `patternProperties`, `propertyNames`, `if`/`then`/`else`, `dependent*`, `prefixItems`, `contains`, `exclusiveMinimum` и `exclusiveMaximum`, `$id`, `$anchor`, `$dynamicRef` и `nullable`. Из draft-07, на котором стоят схемы AsyncAPI, — без `additionalItems`, `dependencies`, `definitions` и `items` в форме списка.
- Без `contentMediaType`, `contentEncoding` и `contentSchema`: league их не проверяет, а читатель примет их за проверку.
- Без булевых схем `true` и `false`, кроме `additionalProperties: true` и `false` — это форма OpenAPI 3.0, её понимает league. Булеву схему в `properties` Redocly не показывает ни одному правилу, и `card_token: true` прошло бы все проверки. Правило `contracts/subset-boolean-schema` проверяет каждое место схемы от родителя и через `$ref`. Схемы привязок AsyncAPI, кроме Kafka, оно не обходит: таких привязок в контрактах нет.
- У медиатипа есть `schema` и нет `encoding`, у параметра и заголовка — `schema`, а не `content`. Ни одно правило не заходит в заголовки `encoding` и в `content` параметров и заголовков: email в `content` параметра прошёл бы мимо правила места персональных данных. Запретить проще, чем учить каждое правило заходить туда.
- В AsyncAPI схема стоит на своём месте, без обёртки `{schemaFormat, schema}`: в обёртке её не читают ни правила сообщений, ни сервисы.
- `type` есть у каждой схемы, кроме чистого `$ref`, в том числе у обёрток `allOf`, `oneOf`, `anyOf` и у схем только с `enum`. Без `type` league пропускает `null` мимо всех ключевых слов, включая `enum`: в `SchemaValidator` `nullable` по умолчанию истинно.
- `type` — одна строка, не массив: массив ломается в параметрах и заголовках и вместе с `items`.
- У закрытой схемы (`additionalProperties: false`) есть непустой `properties` на том же уровне и нет `allOf`: без `properties` league закрытость не проверяет.
- `$defs` — только в корне внешних JSON-файлов. Ссылка на `$defs` внутри YAML-документа даёт `InvalidSchema`, а `$defs` внутри схемы под типами draft-07 правила не обходят.
- Внешний `$ref` — всегда с ведущими `../`, в том числе к соседнему файлу: `../openapi/common.v1.yaml#/…`. Без `./` и без `..` в середине пути: `ReferenceContext::reduceDots` их путает. Имена каталогов в `contracts/` не префиксы друг друга: `Reference::makeRelativePath` сравнивает пути по префиксу строки.
- **Шаблоны:**
  - league собирает их как `#…#u`, без модификатора `D`, и `$` пропускает перевод строки в конце. Поэтому конец строки — `(?![\s\S])`, `$` в шаблонах нет;
  - шаблон держит строку целиком, это проверяет правило `contracts/pattern-anchored`. `pattern` ищется в любом месте значения: без `^` внешний id `a/../x` проходит по хвосту `x`, а без конца строки метка из 13 цифр проходит по первым десяти. Шаблон читают два движка: Redocly — по ECMA-262 с флагом `u`, league — по PCRE. Оба должны увидеть одни и те же якоря, поэтому шаблон:
    - компилируется по ECMA-262 с флагом `u`. Конструкция, которая есть только в PCRE, закончила бы совпадение в league раньше конца строки: после `(*ACCEPT)` проходит любой хвост;
    - начинается с `^` и кончается группой `(?![\s\S])` на верхнем уровне. Совпадения текста на конце мало. В `^(a\(?![\s\S])` скобка экранирована, в `^(a[(?![\s\S])` она стоит внутри класса, и в обоих последняя `)` закрывает группу 1;
    - не содержит `|` вне групп и классов. Альтернатива верхнего уровня держит только один конец строки: `^[0-9]{10}|[0-9]{13}(?![\s\S])` пропускает заголовок, склеенный из двух строк;
    - не содержит `[]` и `[^]`, а внутри класса — `[:`, `[.` и `[=`. В ECMA-262 класс кончается на первой неэкранированной `]`. PCRE читает `]` сразу после `[` или `[^` как литерал, а `[:alpha:]` внутри класса — как POSIX-класс, и класс тянется дальше, до следующей `]`, например в группе конца строки `(?![\s\S])`;
  - исключение одно — шаблон `CacheControlNoStore` в схеме заголовка ответа `Cache-Control`. Он ищет директиву `no-store` в любом месте списка директив, и ровно его там требует правило `contracts/no-store-cache-control`. Схема записывается в самом объекте заголовка, а не через `$ref` на `components/schemas`. Каждое её использование в операциях проверяется через все `$ref`: тот же шаблон в теле, в параметре или в другом заголовке нарушает правило;
  - у моментов — полный шаблон `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z(?![\s\S])`, а не один суффикс `Z(?![\s\S])` рядом с `format: date-time`. Проверка формата в league 0.24, `StringDateTime::__invoke`, хвост не пропускает. Зато пропускает пробел вместо `T`, поля без ведущих нулей и зону с именем на `Z`: `2026-1-1T0:00:00NZ` — это время Новой Зеландии. Календарь шаблон не проверяет: `2026-02-30` и `24:00` проходят, но моменты пишет сам сервис;
  - классы символов — явные, `[0-9]` вместо `\d` и `[A-Za-z0-9_]` вместо `\w`: в PHP модификатор `u` включает `PCRE2_UCP` (`pcre_get_compiled_regex_cache_ex`, PHP 8.4), и `\d` ловит цифры любого письма, а в ECMA-262 — только ASCII;
  - конструкции, которые движки читают по-разному, запрещены, это проверяет правило `contracts/pattern-portable`. Кроме `$` и `\d`, `\D`, `\w`, `\W`, о которых сказано выше, это:
    - `.` вне класса: CR и U+2028 пропускает PCRE, но не ECMA-262;
    - `\s` и `\S`, кроме класса `[\s\S]`: NEL пропускает PCRE, U+FEFF — ECMA-262. `[\s\S]` оба движка читают как любой символ;
    - `\v`: LF пропускает только PCRE;
    - `\b` и `\B`: в «aé» после `a` граница есть только в ECMA-262;
    - `\u`: PCRE его не компилирует, и league отвергает любое значение;
    - обратные ссылки `\1`–`\9` и `\k<…>`: ссылка на группу, которая не участвовала в совпадении, проходит только в ECMA-262, так `^(?:(a)|b)\1` принимает «b» только в Redocly;
    - ретроспектива `(?<=` и `(?<!`: `(?<=a+)` PCRE2 не компилирует;
    - `\P{…}` и `\p{…}`, кроме `\p{L}` и `\p{M}`: другие свойства расходятся именами, `\p{Latin}` компилирует только PCRE;
    - группы модификаторов `(?i:…)`, `(?m:…)` и `(?s:…)`. Это не расхождение, а ловушка: `(?i:[a-z])` в обоих движках пропускает знак кельвина U+212A и длинное s U+017F, а автор ждёт ASCII.

    Расхождения сверены на PHP 8.5.5 с PCRE2 10.44 — так, как проверяет league, — и на Node 24.21.0 из образа Redocly;
  - `\p{L}` и `\p{M}` оба движка читают одинаково, кроме букв новых версий Unicode: и league, и Redocly собирают шаблоны с флагом `u`, но Node 24.21.0 из образа знает Unicode 17.0, а PCRE2 10.44 — только Unicode 15.0. Буква из Unicode 16, например U+1C89, проходит линтер, а league её отвергает. Это расхождение в безопасную сторону: лишнего league не пропустит.
- Обязательные заголовки ответа — с `required: true`.
- У массива есть `items` — одна схема: без `items` элементы могли бы быть любыми.
- Примеры league не проверяет, их проверяет только линтер.
